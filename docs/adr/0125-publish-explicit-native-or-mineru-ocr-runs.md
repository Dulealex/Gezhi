# 发布显式原生文本或 MinerU OCR 运行

`literature resume` 的 OCR 阶段把“是否调用 MinerU”本身作为可审计决定，而不是把原生文本 PDF 当成未经过 OCR 阶段。每个 Active Source 都先由 Core 环境中冻结的 `pypdf==6.14.2` 执行 `native_text_every_page_32_v1` 选择器：PDF 必须至少一页，且每页提取文本去掉 Unicode whitespace 后至少 32 个字符，才选择 `native_text`；零页、任一页不足或 pypdf 不能完成解析/提取，都明确选择 `mineru_ocr` 并保存原因。该规则偏保守，不做质量评分、自动修复或静默 fallback。

两条路径都发布同一种 OCR stage success authority：`sources/<source_id>/ocr/runs/<run_id>/` 是不可变 terminal run，`ocr/current.json` 原子指向完整成功 run。Run 先写入同卷 `ocr/runs/.staging/<run_id>/`，依次保存 `selection.json`、`input.json`、`receipt.json`、输出与除 manifest 自身外全部 regular file 的排序 hash/length/media/schema 清单，readback 后 non-replacing rename；只有完整 success manifest 才能替换 current。随机 `run_id` 只标识一次审计运行；由 Active Source identity、选择器版本与结果、所选 provider profile 形成的 `input_fingerprint_sha256` 才是稳定输入身份。相同 fingerprint 的有效 success 必须复用；完整 run 已 rename 而 current 缺失时只补 pointer。

`native_text` 输出为逐页、保序、未截断的 Canonical JSON，并在 receipt 中明确记录零个 MinerU attempt。`mineru_ocr` 固定使用本机 OCR venv 的绝对 `mineru.exe`、`pipeline` backend、`ocr` method、中文语言和 ADR 0123 的 local/CUDA/offline profile；同时固定 `NO_PROXY=127.0.0.1,localhost`，只让 MinerU client 绕过系统代理访问其同一受控进程树内的本机 API，不移除或放宽外部代理。输入先复制到该 run 的私有目录，MinerU 原始输出、每次 attempt 的 stdout/stderr 与 receipt 全部保留。Provider 输出必须位于固定 `output/mineru/source/ocr` 叶子并通过 no-reparse inventory、必需文件、hash 与 manifest 校验，不按“最大 Markdown”、mtime 或旧缓存猜测结果。

每次 MinerU attempt 的 stdout 与 stderr 共用 `1,048,576` bytes inclusive 上限：恰好等于上限允许，首个超限 byte 立即终止整个 Windows Job；超时、非零退出和输出超限异常都必须携带已经稳定收集的两条有界前缀，且二者合计不超过该上限，不能在分类时丢弃证据。OCR 子进程继承环境前，按 Windows 不区分大小写规则移除全部 `PYTHON*`、MinerU、ModelScope、Hugging Face 与 Transformers policy 变量，再只加入冻结 profile 和 `PYTHONDONTWRITEBYTECODE=1`；外部代理变量继续继承，`NO_PROXY` 精确覆盖为本机 loopback 列表。

Provider 运行期间和返回后都通过 Job 生命周期内的 progress guard 测量 attempt 输出树；每个 regular file 最多 `536,870,912` bytes，两个 attempt provider 输出与最终 MinerU 输出合计最多 `2,147,483,648` bytes、最多 `4,096` 个文件，并在启动前保留至少 `16,777,216` bytes 可用空间。Sparse file 按逻辑长度计量；symlink、reparse point、循环、特殊文件或无法稳定测量的 namespace 一律 fail-stop。后续语义读取还使用更窄的 inclusive 上限：单个 JSON、Markdown 或图片最多 `67,108,864` bytes，单个 PDF 最多 `134,217,728` bytes。Provider success 除固定 inventory 外，还必须验证四份 JSON 的版本化 page/item shape、真实可解析 PDF 的页数与 page box、图片 magic，以及 `source_origin.pdf` 的逐页来源绑定。冻结的 MinerU 3.4.4 会通过 PDFium import/save 重写 processed origin，所以不能要求输出 bytes 等于输入；私有输入自身仍先按 Active Source 长度与 SHA-256 复验，随后 source/origin 必须逐页匹配 media/crop box、rotation、user unit、有界解码后的 content stream hashes，并匹配递归 XObject path、subtype、dimensions 与 raw stream hash。Content stream 只接受无 filter 或无 predictor 的单层 Flate，单份 PDF 的解码总量仍受 PDF 上限约束且最多 `4,096` 个 stream；首个超限、压缩尾随数据或不支持的 filter 都拒绝，不能用无界解压换取兼容。Document metadata、xref/object number 和等价 serialization 不参与该比较。资源越界只有在 terminal audit 能用有界证据完整提交时才可进入 handled failure；否则保持正常 handled receipt 矩阵外并停止新工作。

MinerU 启动前必须重新验证 ADR 0123 的 Python、直接包、配置、模型 manifest、CUDA build 与批准 GPU。运行环境缺失或漂移选择 `ocr_runtime_unavailable`；每次运行最长 900 秒，超时或非零退出最多再以完全相同输入/profile 启动一次全新 attempt，中间固定退避 10 秒，耗尽后选择 `ocr_transient_exhausted`。输出超限、成功退出但输出缺失/越界/无效或其他已确定 provider failure 选择 `ocr_failed`。禁止 GPU 到 CPU、其他 OCR、Ollama、下载、provider/backend/method 切换或复用失败 partial。

Blocked、failed 与 attempt 资产可以作为不可变 terminal audit run 提交，但绝不更新 success current。正常成功后 `.staging` 不留本次目录；崩溃遗留的 partial/unsafe/invalid staging 在原位置 quarantine，不删除、不补成 success。每次 invocation 必须先只读盘点 formal runs、全部 staging success 与 current，证明同一 fingerprint 恰好只有一个可恢复 orphan 后，才允许在紧邻 rename 前重新验证 Data Root / Active Source authority；即使 current 已有效，也不能跳过 staging 分类。新 run 建立 `.staging/<run_id>` 前同样必须紧邻复验 authority，并同时证明 formal 与 staging namespace 都没有该随机 ID。Target 冲突、多个 matching success、UUID 碰撞、rename 结果不确定或 namespace 无法完整证明，均保持普通 handled receipt 矩阵外并立即停止；不得覆盖、换 ID、重试、补 pointer或把它降级成 `recovery_failed` / `commit_failed`。只有能从完整 bytes、manifest 与当前 namespace 唯一证明的 terminal success orphan 才能完成 rename/current；无法证明 Windows child/Job/pipe 已 settle 时同样停止并保留恢复证据。
