# 用 Windows 互斥锁串行化 Knowledge Answer 写入

Knowledge v1 对每个 Knowledge 数据根只允许一个 Answer writer：`knowledge ask` 在生成 `answer_id`、扫描 crash staging 或读取检索快照前，先非阻塞取得字面 `Global\` Windows 内核命名空间中的 mutex。数据根必须先通过既有安全路径校验并拒绝符号链接、junction 与任何 reparse point；锁身份再由已打开真实目录的 `FILE_ID_INFO.VolumeSerialNumber` 与非全零 128-bit `FileId` 加角色版本做固定字节编码后计算 SHA-256，因此同一目录的盘符、大小写、`.`/`..` 或 `\\?\` 拼写不能获得第二把锁。身份 API 失败或 File ID 全零时阻塞，不回退到路径字符串。mutex 一直持有到 Answer 原子提交完成，或任一未提交路径停止全部子进程与 staging 操作、关闭句柄并退出，再以 `finally` 语义释放。mutex 已被占用时，第二个 `ask` 不等待、不排队、不生成 `answer_id`、不创建 staging，也不调用检索或 Codex，只返回待错误合同命名的 busy 结果；`search`、`show` 等只读操作不取得该 writer mutex。操作系统拥有的 mutex 是活跃所有权的唯一权威，PID、时间戳、owner metadata 或固定超时都不能证明进程存活；进程崩溃后 mutex 由 Windows 释放或标为 abandoned，下一 writer 取得它后才有资格处理遗留 staging。Literature 和未来同级 Bot 使用各自隔离的锁，不共享这一串行边界；首版以放弃同一 Knowledge 根上的并行回答换取无第三方依赖、可在一晚实现且不会误回收活跃 staging 的恢复前提，未来可以用新运行版本升级为每 Answer 锁而不迁移既有终态资产。
