# 只从低于 cap 的正式 events 投影 Knowledge usage

Knowledge v1 只有在 ADR 0079 的 capture-finalization boundary 成立、该 ordinal 的固定双文件已经安全关闭并成对安装后，才决定 attempt usage。Writer、terminal validator 与 crash recovery 必须先复验正式 `attempts/NN/events.jsonl` 的固定路径、无参数 `application/octet-stream` identity、实际逻辑长度与 SHA-256，并要求实际长度与 manifest asset `byte_length` 完全相等；令这个已复验的实际长度为 `L`。`L > 16777216` 使资产和 terminal manifest 无效，不能降级为 usage unavailable；`L == 16777216` 时，四项 token 固定全部为 `null` 且 `usage_unavailable=true`，usage consumer 不执行 usage-directed UTF-8 解码、framing、JSON 或 `turn.completed` 投影，也不得复用在线、streaming、provisional 或其他 consumer 已观察到的 usage；只有 `0 <= L < 16777216` 时，才从这份完整、正式且不可变的 events bytes 运行 ADR 0074、ADR 0075 与 ADR 0069 共同定义的唯一严格全流 usage adapter。

这是适用于所有 Knowledge attempts 的 usage-only 保守门禁，不是 overflow 判定。`L == 16777216` 既可能是 events overflow 的 exact prefix，也可能是合法的 exact-cap clean EOF；它不证明或否定 overflow，不锁存 latch、不请求停止 Job、不选择 `failure_class`、不改变 retry 或 Answer 顶层终因。当 events latch 为 false 时，权威 terminal-event adapter 仍可为 provider、runtime、exit 或其他非 usage 分类目的解析 clean-EOF exact-cap events，但无论其中是否存在完整合法的 `turn.completed.usage`，其 usage 都不得进入 manifest；events latch 为 true 的 exact prefix 仍不是完整事件流语义输入。Events overflow 与双 overflow 必然形成 `L == 16777216` 的正式 prefix，因此均得到四项 `null`；final-only overflow 在 `L < 16777216` 时仍可从完整 events 投影 usage，在 `L == 16777216` 时同样保守得到四项 `null`。`final_message.txt` 的长度、内容与 latch 永不参与 token 投影。

在 `L < 16777216` 分支，“整个正式 events”只表示该正式资产的全部不可变 byte sequence，不声称 collector 已取得 provider 的完整 stdout。该序列必须先通过 leading-BOM 拒绝、严格 UTF-8、raw-LF framing、逐 record JSON、任意深度 duplicate-key 拒绝与唯一 `turn.completed` 门禁，不能保留坏尾部之前看似合法的 usage。已知 collector truncation/I/O failure 仍按既有 lifecycle 规则得到 `failure_class=process_error`，但这种未持久化运行时事实不改变 usage eligibility：正式 bytes 自身若严格合法且含唯一 usage-eligible `turn.completed.usage`，字段仍按本 ADR 投影；正式 bytes 自身结构失败才令四项全部为 `null`。没有 usage-eligible `turn.completed`，或其 `usage` 缺失/不是 object 时，四项也全部为 `null` 且 `usage_unavailable=true`；合法 usage object 继续按 ADR 0069 对四个 allowlisted 字段独立验证，合法整数原样保留，缺失或无效字段独立为 `null`，而 `usage_unavailable` 当且仅当至少一项为 `null`。预期的事件内容无效按这些确定性规则得到 `null`；无法读取或复验正式资产、内部 parser 故障或任何无法完成唯一推导的实现失败只能留下 staging，不能伪装成普通 usage unavailable。

本决策不改变 ADR 0068 已冻结的 attempt terminal-signal 时间裁决或 classification-ready 定义。对于 non-overflow attempt，仍在进程、provider、exit 与 usage 全部可分类时记录 classification-ready boundary；正式资产的路径/identity/长度/hash 复验、本 ADR 的长度门禁与低于 cap 时的严格 adapter 都属于既有 usage readiness，其运行时耗时计入 active attempt `elapsed_ms` 并参与当前 30/95-minute deadline 与 interrupt 比较。分类完成后只冻结此前得到的同一 usage 候选值，不重新解析。对于 overflow attempt，ADR 0080 仍在 capture-finalization boundary 后先固定最高优先级 `process_error`，再按本 ADR 冻结四项 token 与 `usage_unavailable`。所有分支都必须在 usage 确定后才采集 attempt `finished_at` / `elapsed_ms` 并冻结十字段 item；overflow item freeze 与 `failed: codex_process_failed`、`stage=synthesis` 仍在同一串行转换。全部 attempts 冻结且 Answer terminal cause 锁存后，`usage_totals` 只按 ADR 0070 从 item 字段逐项求和，不再读取 events；它不属于任何 attempt 的 elapsed 或 95-minute attempt window，但发生在 Answer `finished_at` 前。任一 exact-cap attempt 会使四项总计全部为 `null`。

Terminal validator 与 crash recovery 必须共享同一 usage 推导：`L == 16777216` 时逐字段要求四个 `null` 加 `usage_unavailable=true`；`L < 16777216` 时从正式 events 重新运行唯一严格 adapter，并要求五个 usage 字段与重算结果完全相等。Recovery 不从 `failure_class=process_error` 反推 collector truncation，也不让后验复算回计原运行的 attempt/Answer 时钟或 95-minute window；它只复验并补交已经拥有完整有效 terminal manifest 的 staging，不补写 token、不修复 events、不重新选择运行时分类，也不重新运行 Codex、Answer validation 或任何工作流阶段。该决定无需新增 overflow/exact-cap 字段、marker、sidecar、配置、错误码、枚举、持久资产或第三方依赖；`TerminateJobObject` 内部退出 DWORD、overflow 外部诊断及未来是否为诊断目的解码或展示原始 prefix 继续另行冻结。
