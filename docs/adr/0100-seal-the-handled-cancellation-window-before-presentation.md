# 在 presentation 前封闭 handled cancellation window

`knowledge.ask` 只有先经过 [ADR 0110](./0110-run-a-decoded-argv-resource-preflight-before-typer.md) 的 project-wide `RawArgvPreflightV1` seam、再按 [ADR 0111](./0111-lazy-import-the-cli-framework-and-command-graph-after-argv-preflight.md) 在 PASS 后 lazy-import Typer、Rich 与完整 command graph，并按 [ADR 0113](./0113-feed-one-immutable-argv-snapshot-to-preflight-and-typer.md) 把唯一 immutable snapshot 的 exact argument suffix 显式交给 Typer，由 parser 成功识别 `knowledge ask`、完成 command/subcommand/option grammar、保留全部 recognized raw values 并决定进入 handled adapter 后，才为本 invocation 建立 command-owned `HandledCancellationWindowV1`；[ADR 0114](./0114-exclude-argv-zero-from-raw-argv-resource-measurement.md) 已冻结上述 preflight 的全部资源计量只覆盖 suffix、完全排除 argv0，[ADR 0115](./0115-cap-raw-argv-at-128-arguments-8192-elements-each-and-16384-total.md) 已冻结三个 inclusive raw ceilings 与 `len(str)` 计量，[ADR 0116](./0116-return-2-with-one-fixed-stderr-line-for-raw-argv-resource-violation.md) 已冻结超限时由最小 bootstrap presenter 输出 fixed stderr、empty stdout 并返回 `2`。所选 cancellation profile 的 lifecycle/control state 初始化与 activation 必须在 Question validation、configuration、provenance、Data Root 或任何其他领域 gate/probe 前证明成功。Bridge 的生命周期状态固定为 `OUTSIDE -> ARMED_PASS_THROUGH -> ACCEPTING -> SEALED_PASS_THROUGH -> RELEASED`：只有 `ACCEPTING` 是 handled window，第一项领域工作只能在进入该状态后 commitment；interactive profile 必须证明自身 registration，no-source profile 则必须证明本 invocation 从未建立 Gezhi-owned registration。RawArgvPreflight resource violation 发生在 command recognition 前，不建立 JSON/Human handled result、diagnostic、cancellation profile/control state 或 latch，也不进入本 ADR 的 handled presentation；其 fixed bootstrap presentation 可以 production 使用。Activation 前的 Ctrl+C 与 parser/argument failure 同样不写 ADR 0098 latch。Profile identity、activation 或 ownership 无法证明时不得启动领域工作，也不形成正常 envelope 或 normal-return exit。

每次 Ctrl+C callback 的 admission 与最终 command-state seal 必须在 ADR 0098 的同一 command-owned 串行状态域竞争。Callback 在 `ACCEPTING` 先赢时，只可一次性锁存取消事实与首次 `observed_monotonic_ns`，并把本次 invocation 记为 accepted；重复 Ctrl+C 不改写 latch，但该次 callback 仍按 accepted 处理。Callback 对本次事件的 accepted/pass-through 裁决一经取得不得在返回前因 phase 改变而重解释；Ctrl+Break、close/logoff/shutdown 与其他未批准 control type 在所有 phase 都是 pass-through。只有领域执行、适用的 committed/no-commit safe-finalization、result/diagnostic 构造与验证全部完成后，唯一编排器才可建立 final candidate 并在同一串行转换中锁存 immutable final `outcome`、`result`、`diagnostics` 与该 mode 已批准的 presentation disposition，再把 bridge 从 `ACCEPTING` 转为 `SEALED_PASS_THROUGH`；[ADR 0107](./0107-seal-one-bounded-immutable-knowledge-ask-json-buffer.md) 已把 `knowledge.ask --json` disposition 闭合为 pre-seal `READY_BYTES` 或 `NO_OUTPUT_PRESENTATION_FAILURE`。Callback 先赢则 seal 必须观察取消、废弃整个 candidate 并重新走适用仲裁，seal 先赢则后来 callback 不得再触碰 latch、outcome、result、diagnostics、presentation disposition、cleanup 或 commit。

进入 `SEALED_PASS_THROUGH` 后，编排器必须按所选 profile 证明 accepted-in-flight 为零并完成 source-specific release，最后才转为 `RELEASED`。Interactive profile 先排空全部在 seal 前已经赢得 accepted admission、仍可能触碰 invocation state 的 callback，再撤销 Gezhi 自己的 bridge registration 并证明 matching removal 成功；unregister 成功本身不作为 callback quiescence 证据。No-source profile 则证明 accepted-in-flight 恒为零且本 invocation 从未建立 Gezhi-owned registration，不执行 removal call。可能被底层运行时延迟调度的 interactive pass-through callback 不得访问 invocation-owned mutable state，所需最小 routine/control block 必须保持到 adapter 能证明安全的生命周期终点。该协议只证明 Gezhi 自己不再接受或拥有 Ctrl+C，不枚举、清空、重建或声称恢复整个 prior/default handler list，也不以切换全局 Ctrl+C-ignore 属性冒充 matching removal。

后续 [ADR 0101](./0101-use-a-project-owned-native-win32-ctrl-c-bridge.md) 已把 interactive adapter 冻结为 process-pinned、项目自有的 native Win32 DLL：C handler 与 conditional seal 共享原子 admission gate，Python 只从主编排线程调用导出接口；[ADR 0102](./0102-normalize-inherited-ctrl-c-ignore-before-activation.md) 已冻结 interactive candidate 的 inherited-ignore normalization，[ADR 0103](./0103-require-a-read-only-conin-processed-input-capability-gate.md) 已冻结只读 console/processed-input 候选门禁，[ADR 0104](./0104-continue-with-a-no-source-cancellation-profile-when-capability-is-absent.md) 已冻结 `capability_absent` 的 no-source lifecycle、零 drain 与 never-registered release proof，[ADR 0105](./0105-use-the-no-source-profile-when-the-current-process-is-being-debugged.md) 已冻结当前进程 debugger gate 与静默 no-source selection，[ADR 0106](./0106-run-command-owned-children-without-a-console.md) 已冻结 orchestrator-owned Codex attempt root 的 no-console、no-process-group、stdio/handle allowlist 与 Job handoff。

JSON/Human presentation 只能在 `RELEASED` 后开始。Seal 之后的 Ctrl+C 完全交给实际存在的 prior/default 处理语义，可能被消费、允许进程继续或终止进程，但绝不能重分类已锁存的领域状态、再次 cleanup、回滚 commit、生成新的 interrupted envelope，或由 Gezhi bridge 选择应用级 normal-return `130`。Presentation 因此可能留下零字节、immutable output 的前缀或完整 envelope；不得重试、修补 prefix、追加 fallback JSON/Human 文本或根据 Ctrl+C 重算状态。完整 receipt 已被调用方取得后仍是既有 process-level acknowledgment；只有完整 presentation 成功且沿 handled return 返回时，既有 outcome-to-exit table 才适用，外部/default termination 的数值即使偶合 `130` 也不是该表的应用级 `130`。Profile identity/activation、zero-in-flight、source-specific release 或状态/ownership 证明失败均位于正常矩阵外，不新增第八项 `failed` 或第四种 outcome。ADR 0107 已冻结 `knowledge.ask --json` 的 65,536-byte inclusive cap、pre-seal exact buffer、no-output failure disposition 与 same-buffer write；[ADR 0108](./0108-return-1-for-controlled-knowledge-ask-json-presentation-failure.md) 已把 seal/release 完整且无 pending write 的可控 no-output/setup/write failure 静默映射为 `1`，但绝不接管上述 profile/ownership failure 或外部实际终止。
