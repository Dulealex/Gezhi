# 使用两个启动 adapter 与一个 bootstrap seam 打包 Gezhi

根目录 uv project 从 non-packaged virtual application 改为可安装的 Python distribution：使用 `src/gezhi/` layout、`[tool.uv] package=true`、`uv_build>=0.11.26,<0.12` 与 `build-backend="uv_build"`，并以 `[project.scripts] gezhi="gezhi.bootstrap:main"` 生成项目环境内的 `gezhi` console script。项目锁定的 uv 0.11.32 是唯一受支持的 build frontend；其兼容 bundled `uv_build` 满足本 build requirement。`uv_build` 是 build-system dependency，不加入 Gezhi runtime dependencies，也不授权在业务实施期间改变既有 Python/npm 依赖图。本 Python build backend 不编译 native extension；它不修改或排除 ADR 0101 已冻结、由独立 MSVC 流程形成并由标准库 `ctypes.WinDLL` 加载的项目自有 x64 cancellation bridge，也不提前冻结该 DLL 以后是否作为预构建 package data 交付。

产品只有一个 `gezhi` CLI，但允许两个 launcher adapter：项目环境生成的 `.venv\Scripts\gezhi.exe` 与 `.venv\Scripts\python.exe -m gezhi`。两者都必须恰好调用同一个无参数 `gezhi.bootstrap:main` seam；`src/gezhi/__main__.py` 只能把 module execution 交给该函数并以其整数结果结束进程，不得复制 argv snapshot、preflight、lazy import、command graph、presentation 或 exit 仲裁。PowerShell/批处理 wrapper、Typer 自带 `typer.exe`、全局 `uv tool` 安装与第三个项目 launcher 都不是产品入口。

两个 adapter 都必须保持 [ADR 0110](./0110-run-a-decoded-argv-resource-preflight-before-typer.md) 与 [ADR 0111](./0111-lazy-import-the-cli-framework-and-command-graph-after-argv-preflight.md) 的同一顺序：CPython 形成各自的 `sys.argv` 后进入薄 bootstrap，`RawArgvPreflightV1` 恰好运行一次，只有 PASS 后才允许项目 lazy-import Typer、Rich、CLI app factory、完整 command graph、`open_gezhi()` composition 与任何 Context command adapter。`src/gezhi/__init__.py`、`__main__.py`、bootstrap、preflight module 及其 PASS 前 project-owned import closure 不得预载或构造这些后置模块。[ADR 0113](./0113-feed-one-immutable-argv-snapshot-to-preflight-and-typer.md) 已冻结两个 adapter 都在这个唯一 bootstrap 内恰好一次形成 immutable snapshot，并以相同规则交给 preflight 与 Typer；console script 与 `python -m` 的 `argv[0]` 可能不同，[ADR 0114](./0114-exclude-argv-zero-from-raw-argv-resource-measurement.md) 已冻结这种差异不参与任何资源计量，[ADR 0115](./0115-cap-raw-argv-at-128-arguments-8192-elements-each-and-16384-total.md) 已冻结两者共用的三个 inclusive ceilings 与 `len(str)` 计量，[ADR 0116](./0116-return-2-with-one-fixed-stderr-line-for-raw-argv-resource-violation.md) 已冻结两者共用的 fixed fd2 presentation 与 process exit `2`。两个 adapter 都必须透传同一个 `main()` result，不复制 presenter 或建立 launcher-specific fallback；其余 bootstrap/internal 与 parser/argument failure 仍待后续决策。

`gezhi.bootstrap:main` 是 launcher caller 与测试共同使用的稳定 interface；它隐藏启动排序、preflight handoff 与后置 graph loading。`open_gezhi()` 继续是 ADR 0032 冻结的唯一领域 composition interface，不从 package `__init__` 重导出，也不在 bootstrap PASS 前调用。Typer app factory、command registration 和 Context adapters 都是 bootstrap seam 后的私有 implementation；本 ADR 不把它们变成新的 public interface。

Literature、Knowledge 与未来 Bot 继续作为 repository-owned 静态同级 module，由 PASS 后的 command graph 与 `open_gezhi()` 显式装配；不得使用 Python package entry-point discovery、目录扫描、动态 plugin registry 或每 Bot 独立 executable。除了 `src/gezhi/` module root、inert `__init__.py`、双 adapter 与唯一 bootstrap target 外，本 ADR 不冻结私有文件名、子 package 布局或 app-factory interface。

本次 packaging window 只建立可构建、可安装的空 package root 与 launcher metadata；在 bootstrap/preflight implementation 形成前，不把生成的 executable 宣称为已通过 runtime contract smoke。验收必须先证明 uv 能以 frozen project metadata 安装 editable Gezhi distribution、生成唯一 `gezhi` console entry point，且 entry-point target 精确为 `gezhi.bootstrap:main`；后续实现验收再通过两个真实 adapter 证明 preflight 次数、negative import set 与相同 post-PASS graph。Module/package 定位或 console-script stub 自身失败发生在 bootstrap 前；PASS 后 import/graph failure 仍保持 ADR 0111 的 bootstrap/import failure 语义。

该选择增加一次业务实施前的受控 packaging baseline 更新，换取从任意工作目录调用的正式 Windows `gezhi` 命令、隔离源码与 installed package 的 `src` layout，以及两个 adapter 对一个 deep bootstrap interface 的共同复用。它不增加运行时依赖、产品命令、动态扩展机制、领域 Schema、diagnostic code、持久资产或模型调用。
