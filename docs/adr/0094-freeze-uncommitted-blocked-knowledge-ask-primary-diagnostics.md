# 冻结未提交 knowledge.ask 的 blocked 主诊断

> Supersession note: [ADR 0117](./0117-freeze-context-scoped-data-root-cli-overrides.md) 只替换本文尚待 source-specific contract 冻结的 provisional `--data-root` / `--timeout` token witnesses：V1 的规范 root options 是 `--literature-data-root` / `--knowledge-data-root`，而 `--data-root` / `--timeout` 均为 parser-unknown。本文保留为历史决策记录；其 Question → Configuration gate 顺序、cause、diagnostic、exit 与其余边界不受替换。

本次新 Answer 的 final checkpoint 已通过、Root trust 仍成立且 expected target 不存在时，non-replacing same-volume directory rename 返回非 target-conflict 失败；随后又能证明 staging 仍未提交、target 不是本次 commit、全部操作已安全停止，才使用 `{"code":"knowledge.ask.answer_commit_failed.v1","context":{}}` 返回 no-commit `failed`、`result=null` 与正常 JSON exit `1`。不得自动重试；包含完整 terminal manifest 的 staging 原地保留，只能由后续 orphan recovery 独立复验后补交。Target-exists 使用 `answer_target_conflict`，root trust loss 使用 `data_root_integrity_lost`。若无法证明 rename 是否已提交，不得声称 `result=null` 或使用本码，路径位于正常 JSON 矩阵外。

本次新 Answer 的 expected `answers/<answer_id>/` target 在最终 checkpoint 已存在，或 non-replacing directory rename 明确报告 target-exists，且 Root trust 仍成立时，唯一 primary 为 `{"code":"knowledge.ask.answer_target_conflict.v1","context":{}}`，配 no-commit `failed`、`result=null` 与正常 JSON exit `1`。不得覆盖、合并、删除、比较后复用既有 target，也不得生成替代 `answer_id` 自动重试；本次 staging 原地隔离。既有 target 即使完整有效且内容相同，也不能冒充本次 commit。历史 orphan candidate 的 target conflict 仍只作 supplemental；root trust loss 由 `data_root_integrity_lost` 优先，其他 rename failure 另行分类。

本次新 Answer 已进入 terminal manifest formation 且 Root trust 仍成立时，若 canonical manifest buffer 构造或 65,536-byte inclusive cap、direct `CREATE_NEW` 等价 leaf formation、write/completion/close、安全 readback、Schema/canonical byte identity、目录资产闭合或跨资产复验任一步失败，则使用 `{"code":"knowledge.ask.answer_manifest_failed.v1","context":{}}` 返回 no-commit `failed`、`result=null` 与正常 JSON exit `1`。Partial、既存或无效 manifest 留在 staging，不删除、修补、重写或规范化。该 code 只属于本次新 Answer；历史 orphan manifest 无效仍是 supplemental。Manifest formation 前的 non-terminal asset failure 使用 `answer_staging_failed`，root trust loss 使用 `data_root_integrity_lost`，expected target conflict 与最终 directory rename failure 另行分类。

本次新 `answer_id` 已生成后，若 Root trust 仍成立，但 `answers/.staging/<answer_id>/` 无法安全创建，任一 non-terminal asset 无法形成/写完/验证/安装，或 writer-private spool/tail/temp 无法撤销而不能达到封闭 terminal asset set，则只要能够安全停止并形成 handled envelope，使用 `{"code":"knowledge.ask.answer_staging_failed.v1","context":{}}` 返回 no-commit `failed`、`result=null` 与正常 JSON exit `1`；已有 staging 原地隔离。该 code 不覆盖 terminal `manifest.json`、expected target conflict 或最终 directory rename failure。若原业务/runtime failure 仍能成功提交 `status=failed` Answer，则走 committed matrix；若 root trust 丢失，`data_root_integrity_lost` 优先。

取得 Answer writer ownership 后、生成本次新 `answer_id` 前，若 root trust 仍成立但 `answers/.staging/` 无法安全枚举，或 invocation-wide orphan scan protocol 无法建立/完成，当前命令以 `{"code":"knowledge.ask.orphan_scan_failed.v1","context":{}}` 返回 no-commit `failed`、`result=null` 与正常 JSON exit `1`；不得继续生成身份、检索或调用 Codex。若失败同时证明 Data Root trust 已丢失，`knowledge.ask.data_root_integrity_lost.v1` 优先。单个 orphan basename/manifest 无效、target conflict 或 candidate-local recovery rename failure 仍只产生 supplemental，保持原现场并继续扫描，不得升级为本 primary。

Question、Configuration 或 Provenance gate 的 caller-owned value/facts 已经通过相应规则后，若 Gezhi 仍无法机械构造或 canonical-serialize `QuestionEnvelopeV1`、immutable role descriptor 的 audit bytes、或合法 Git facts 对应的 provenance object，这不是 caller-blocked。只要能够安全收尾并形成 handled envelope，统一选择 no-commit `failed`、`result=null`、正常 JSON exit `1`，唯一 primary 为 `{"code":"knowledge.ask.pre_answer_formation_failed.v1","context":{}}`。该 code 不区分三个内部构造点，不披露 exception、内部字段或序列化细节，也不得作为 blocked、committed 或 supplemental item；内存耗尽、内部不变量破坏或无法形成诊断的路径仍可能位于正常矩阵外。

V1 的 filesystem threat model 不包含恶意或高权限本机进程在检查与使用之间并发替换目录组件。实现仍必须在 Data Root preflight、创建本次 invocation 的 staging 直接子目录之前，以及任何正式或 recovery staging-directory rename 之前，复核冻结 root handle 的 physical identity、handle-derived canonical root、目标父链与 reparse 状态；发现漂移必须停止。所有 descendant path 只能从冻结 canonical root 派生，禁止重新使用 raw configured path。V1 不要求每次 descendant open/create/rename 都使用 handle-relative Win32/NT API，也不承诺消除最后一次复核与实际操作之间的 hostile TOCTOU。

每次 Context command 的 Data Root gate 只允许 safe-open 并验证该命令自己消费的 Context root；不得探测其他 Context root 的存在性、可访问性、句柄或 physical identity，也不得让无关 Context 的 Data Root 状态阻塞本命令。全局 root 隔离仍先由 Configuration gate 对全部 final path strings 做无 I/O 的纯词法比较。

V1 只承认 Windows 大小写语义、separator `\` / `/`、`.` / `..` 的合法词法归一，以及普通 DOS 与等价 local extended DOS `\\?\` 前缀之间的路径等价。当前 root safe-open 后若发现输入依赖 8.3 short name、SUBST、额外 drive-letter、volume mount 或其他隐藏 filesystem alias，选择 `data_root_unsafe`；无法完成别名/最终路径判定但尚无 unsafe 肯定证据时继续选择 `data_root_unavailable`。此严格 no-hidden-alias rule 让当前命令无需为了物理隔离而打开所有其他 Context roots。

[ADR 0110](./0110-run-a-decoded-argv-resource-preflight-before-typer.md) 已在本矩阵和 Typer grammar 之前冻结 project-wide `RawArgvPreflightV1` seam 与职责：所有公开 CLI invocation 都先经过这层；它只拥有对 CPython 已解码、尚未被 Typer 解释的 immutable argv snapshot 执行静态资源 ceiling 机械检查的职责，不得先识别 command、`--json`、Human、help、version 或 known/unknown token，也不执行 grammar、类型/range/path/configuration 或领域校验。只有该 seam 通过后，[ADR 0111](./0111-lazy-import-the-cli-framework-and-command-graph-after-argv-preflight.md) 才允许项目 lazy-import Typer、Rich 与完整 command graph，随后 Typer parser 才处理 command/subcommand/option grammar；[ADR 0113](./0113-feed-one-immutable-argv-snapshot-to-preflight-and-typer.md) 冻结 preflight 与 parser 的唯一 immutable argv snapshot、exact value/order feed-through、固定 `prog_name="gezhi"`、关闭 Windows expansion 与 shell completion，[ADR 0114](./0114-exclude-argv-zero-from-raw-argv-resource-measurement.md) 冻结全部资源计量排除 argv0，[ADR 0115](./0115-cap-raw-argv-at-128-arguments-8192-elements-each-and-16384-total.md) 冻结 suffix count `128`、单 token `8192` 个 Python `str` 元素与 aggregate `16384` 个元素的 inclusive ceilings，[ADR 0116](./0116-return-2-with-one-fixed-stderr-line-for-raw-argv-resource-violation.md) 冻结无 payload resource verdict、固定 stderr bytes、空 stdout 与 exit `2`。未知命令或选项、recognized option 完全缺少参数、重复或互斥规则违反仍是 argument failure。Parser 对已经识别的 `knowledge ask` 必须把 Question text 与 configuration override 保留为 raw string representation 交给 handled adapter；不得提前执行整数/enum/path 类型转换、范围或 required-domain-field 校验、文件存在性/reparse probe、Git 查询或 mutex operation。空 Question 与 raw `--timeout nope` 同时出现时先由 Question gate 选择 `invalid_question`；Question 成功后才可由 Configuration gate 把后者选择为 `configuration_invalid`。Resource violation 与 parser/argument failure 都位于本矩阵和 handled JSON/Human result 之外，不能映射成本 ADR 的 blocked/failed/interrupted 或 diagnostic；前者现已由 ADR 0116 使用独立 bootstrap presentation/exit，后者仍由后续 parser contract 决定。

只有 invocation 已通过 ADR 0115 的 raw resource preflight、Typer grammar 成功并进入 handled Question gate 后，本段顺序才适用。Question gate 复用 `QuestionEnvelopeV1` 与查询原子的既有确定性规则，并按唯一 fail-fast 顺序选择。首先检查 NUL、非配对 surrogate、除 TAB/LF 外的 `Cc`，完成 CR/LF、NFC 与 `strip()` 规范化；任一非法或规范化后为空选择 `invalid_question`。其次检查最终规范值是否超过 2000 Unicode code point 或 8192 UTF-8 bytes，超限选择 `question_too_large`。只有规模合法才检查纯符号或只含一个 Han 字符，命中选择 `invalid_question`；最后形成查询原子，任一路去重后超过 128 项选择 `question_too_complex`。因此在已经通过 raw preflight 的输入中，规范 Question 超长且含禁止 control 时选择 `invalid_question`，规范 Question 超长且为纯符号时选择 `question_too_large`，规模合法的纯符号输入选择 `invalid_question`。原始谓词可以重叠，但顺序保证选中 cause 唯一；`invalid_question` 只覆盖本段逐项列出的条件，不是任意输入 catch-all。当前公开 CLI 只接受 question text，不增加 `question_envelope_invalid`。Caller-owned Question 已合法，但 adapter 在受控构造边界内无法形成或 canonical-serialize 合法 `QuestionEnvelopeV1`，且仍能安全收尾并形成 handled envelope时，按 ADR 0095 选择 `knowledge.ask.pre_answer_formation_failed.v1`；若错误形状/类型已经逃出该构造边界，说明内部不变量被破坏，不得把该 code 扩成 catch-all，路径位于正常矩阵外。无法安全形成诊断的资源耗尽等情况同样位于正常矩阵外。

Configuration source 的发现与验证顺序固定为 CLI → `GEZHI_*` → local TOML → default TOML → 程序安全默认值；它与既有 override precedence 使用同一顺序。程序安全默认值是完整、内置且可信的最终基线，不是外部文档。`config/default.toml` 是 Git 管理、无秘密、必须存在的版本化局部覆盖文档；`config/local.toml` 是 Git 忽略、无秘密、可选的版本化局部覆盖文档。两份 TOML 都不必填写全部最终字段，但 active 文档必须声明 string `config_version`。其合法 grammar 精确为 lowercase ASCII `gezhi.config.vN`，其中 `N` 是无前导零的正十进制整数；当前程序只支持 `gezhi.config.v1`。Missing、非 string 或 grammar-invalid 值选择 `configuration_invalid`，grammar-valid 但 unsupported generation 选择 `configuration_incompatible`。Default 与 active local 必须声明同一 generation；即使未来程序同时支持多代，跨代 TOML patch 也禁止合并并选择 `configuration_incompatible`。CLI、`GEZHI_*` 与安全默认值隐式绑定当前程序 generation，不携带也不允许设置 `config_version`；该 document metadata 不进入最终 runtime config 或 `effective_config.json`。Local 合法缺席直接跳过；default 缺失，或任一已存在文档无法安全读取，进入错误裁决。`.env` 只可能属于后续单独冻结的秘密加载，不参与这套非秘密配置 merge 或 cause 顺序。

第一个 active source 的权威错误停止后续 source 验证，不能由较低优先级 source 覆盖；例如环境变量值无效且 local TOML 版本不兼容时选择 `configuration_invalid`，local TOML 版本不兼容且 default TOML 语法损坏时先选择 `configuration_incompatible`。每个 source 只验证自己 source envelope 的必填键以及实际提供字段的名称、表示、类型和局部约束；未知字段一律拒绝。缺少某个最终业务字段不使局部 patch 自身无效，只有全部 source 成功合并后才验证 final required fields 与跨字段不变量，因此单独 raw `--data-root X` 可以是合法 CLI patch。

Merge 不是任意 dict update，而是由 closed configuration Schema 拥有的类型化叶字段操作。对每个已知 leaf path，按 CLI → `GEZHI_*` → local TOML → default TOML → 安全默认值选择第一个 present value；高优先级 nested table 只覆盖实际提供的 leaf，未提供的 sibling 继续从较低 source 取得。Scalar 与 array 都是 atomic value，array 只能整体替换，禁止拼接、逐项 merge 或去重。V1 不接受 JSON/TOML/CLI `null`、unset、delete marker 或 tombstone；要恢复低优先级值只能移除较高 source 的 override。空字符串是 present value，不是 absent，是否有效由该字段 Schema 决定。重复 CLI option 是 parser grammar failure，重复 TOML key 是 `configuration_invalid`；即使某个低优先级字段最终被覆盖，其 source 仍必须先完整通过自身验证。

单个 Configuration source 内按唯一顺序运行。无法安全读取、TOML 语法错误、根结构或基础 decode 错误，以及版本化 TOML patch 的 `config_version` 缺失、非 string 或 grammar-invalid，选择 `configuration_invalid`。若 generation grammar 合法但不受支持，选择 `configuration_incompatible` 并停止，不得用当前 generation 的字段规则解释未知 generation；因此同一文档还含未知字段时仍由 incompatibility 获胜。只有受支持 generation 才继续严格检查 source-owned required key、unknown/supplied 字段、字段类型与局部范围，任一失败选择 `configuration_invalid`。全部 active source 成功后先要求 TOML generation 相同，再用上述 typed-leaf operator 合并并验证 final required fields 与跨字段不变量；generation mismatch 选择 `configuration_incompatible`。V1 的 `configuration_incompatible` 只覆盖 grammar-valid unsupported generation 或 active TOML generation mismatch；以后只有新合同明确批准的 compatibility predicate 才可扩展，不能把任意合法配置值临时归入该 cause。

V1 external configuration 的 final runtime 字段闭包只有两个 nonempty string leaf：`literature.data_root` 与 `knowledge.data_root`，内置安全默认值分别为 `E:\Gezhi\data\literature` 与 `E:\Gezhi\data\knowledge`。两者由各自 Context table 静态拥有；任一 future Context 必须通过新 configuration generation 显式增加自己的 table，V1 不接受动态 context map、unknown table 或其他 leaf。两项都由完整内置基线提供，所以 TOML partial patch 可以省略；全部 source 合并后必须存在。Non-string 或空字符串在 Configuration gate 选择 `configuration_invalid`；非空字符串不得由 Pydantic `DirectoryPath`、exists 或 reparse validator 提前探测。

所有 Context Data Root 的规范化 Windows path namespace 必须两两不同且互不构成祖先/后代。任一 Data Root 都不得等于项目根 `E:\Gezhi`，也不得包含该项目根；位于项目根内部时，它必须是共享容器 `E:\Gezhi\data` 的严格后代，不能直接使用 `E:\Gezhi\data`。项目外的本机根仍允许。该规则同样约束未来 Context 的显式 root，使任何两个 Context 都不能共享或嵌套 ownership namespace。

Configuration gate 在全部 source 合并后，只对能够无文件系统 I/O 纯词法归一为本机 DOS 绝对路径的 final root values 执行 cross-field isolation comparison；separator、`.` / `..`、local extended DOS 前缀与 Windows 大小写语义的等价形式先归一。若此时已经能证明两项相同、祖先/后代，或某项侵犯项目根/共享 `data` 容器边界，选择 `configuration_invalid` 并停止，不进入 Provenance 或 Data Root gate。无法在这一层形成受支持本地绝对路径的 namespace 不得被误报为配置重叠，仍由后续 Data Root gate 按自身规则裁决。若文本配置通过，但 safe open 后由 reparse evidence、handle-derived final path 或 physical identity 才证明隐藏别名、真实对象重合/嵌套或物理边界冲突，则选择 `data_root_unsafe`。Configuration gate 禁止为了隔离比较而访问文件系统。Source-specific CLI/env name 仍待冻结。

`knowledge_answerer_v1` 的 model、reasoning、Codex CLI version、attempt timeout/window/backoff/count、检索/捕获/Schema/cap 与其他 role/runtime policy 都不是 TOML、CLI 或 `GEZHI_*` field；任一 source 提供这些名称时作为 unknown field 选择 `configuration_invalid`，不建立“只能填固定值”的假旋钮。`effective_config.json` 继续保存 timeout/window/backoff，但它由 immutable role descriptor 生成，是 Answer 审计资产，不是用户配置回显。`--json`、Question、PDF path、review decision 与其他 invocation/presentation value 也不进入 configuration。Configuration gate 成功时必须同时冻结合并后的 deployment config，以及从 role descriptor 形成并已经 canonical-serialized 的 effective-config bytes；ID 后只写同一冻结值/bytes。构造、序列化或其他内部机械失败只有在能够安全收尾并形成 handled envelope 时才留给 no-commit `failed`。程序安全默认值或 role descriptor 违反自身不变量、内存耗尽或无法构造诊断时不得伪装成 blocked，且仍可能位于正常矩阵外。

Provenance gate 必须在生成 `answer_id` 前形成 ADR 0063 的封闭 object。Git 查询失败、输出非法，或取得的 Git facts 不能机械映射为 `clean|dirty|unborn` 及其合法 revision 组合时选择 `provenance_unavailable`；`dirty` 与 `unborn` 本身都是合法状态，不得阻塞。合法 Git facts 已取得后的 object 构造、序列化或其他内部机械失败不属于该 cause；只有能够安全收尾并形成 handled envelope时才留给 no-commit `failed`，否则仍可能位于正常矩阵外。Codex CLI/模型能力不可用也不是 provenance failure，而是在 Answer 生命周期内按既有 committed `codex_runtime_unavailable` 处理。Primary 不披露仓库路径、branch、remote、changed files、revision、Git 原始输出或异常。

Configuration 与 Provenance gate 成功后必须冻结各自已经验证的安全内存值；生成 `answer_id` 后写入 Answer staging、`effective_config.json` 与 terminal manifest 时只能复用同一值，不得在持锁期间或 ID 后重新读取配置、重新查询 Git，或因工作树随后变化改写 provenance。Answer writer mutex 不保护 Git 仓库或配置 source。

Data Root gate 只支持本机 non-remote Windows volume。输入可以是普通 DOS drive-absolute path（如 `D:\Research\Knowledge`）或等价的 local extended DOS `\\?\D:\...`；`/` separator 与 `.` / `..` 仅作为输入 alias，必须先纯词法规范化，且 `..` 不得越过 volume root。位于 `E:\Gezhi` 外的本机绝对根本身合法，不构成 escape。Relative、drive-relative、root-relative、UNC/extended UNC、`\\wsl.localhost\...`、映射 remote drive、`\\.\`、`GLOBALROOT`、Volume GUID、其他 NT/device namespace、alternate data stream 或 drive separator 之外的 colon 都是明确不受支持的 ownership namespace，选择 `data_root_unsafe`。V1 不用 `Global\` mutex 冒充跨主机协调。

对通过 namespace grammar 的本地路径执行逐组件 no-follow/reparse-aware 检查。路径组件或 leaf 明确为 symlink、junction、其他 reparse point，或 broken target 仍留下明确 reparse evidence 时选择 `data_root_unsafe`。尚无 unsafe 肯定证据，而目录缺失、不是 ordinary directory、拒绝访问、无法取得目录句柄，或打开后无法完成 handle-derived final/resolved-path 核对时选择 `data_root_unavailable`，不得猜测它也许不安全；`knowledge ask` 不自动创建 Data Root。只有 safe open、final path 与全部边界验证成功后才在同一 handle 查询 ADR 0052 physical identity；`FileIdInfo` API/structure 失败或 16-byte `FileId` 全零选择 `data_root_identity_unavailable`，但 API 成功且 FileId 合法时 `VolumeSerialNumber=0` 仍有效。Primary 不披露路径、权限、volume、FileId、Win32 code 或原始异常。

成功验证的真实 Data Root handle、从该 handle 取得的 physical identity 与由该 identity 导出的 mutex name 必须保持同一对象绑定；实现不得计算 mutex name 后关闭 handle，再从 raw configured path 重开 root。Descendant 操作只从冻结的 handle-derived canonical root 派生，并执行本 ADR 规定的 checkpoint revalidation；这不等于每个 descendant operation 都由 root handle 相对寻址，也不构成 hostile concurrent namespace mutation 下的 race-free 保证。

初始 Data Root gate 是本 invocation 使用 `data_root_unavailable`、`data_root_unsafe` 或 `data_root_identity_unavailable` blocked primary 的唯一窗口；gate 成功即不可逆锁存。之后无论是否已经生成 `answer_id`，持锁 recovery、staging 创建前或最终 rename 前的 checkpoint 若无法继续证明 root identity/canonical path/父链/reparse 状态仍安全且相同，都属于运行期完整性故障并选择 no-commit `failed`，不得倒退重分类为 `blocked` 或复用三项 blocked code。Root 已失去信任时禁止再写 terminal `status=failed` Answer；本次新 staging 若存在则原地隔离，`result=null`。只有 ADR 0099 `NoCommitSafeBoundaryV1` 与 handled envelope 仍可完成时才进入正常 failed matrix，否则沿 ADR 0093 留在正常矩阵外。该分支的唯一 primary 固定为 `{"code":"knowledge.ask.data_root_integrity_lost.v1","context":{}}`，正常 JSON exit 为 `1`；它既覆盖明确漂移，也覆盖强制 checkpoint 无法重新建立安全性/同一性证明，不披露 path、file identity、permission、Win32 code 或异常文本。该 code 只作 no-commit failed primary，不得作为 blocked、committed 或 supplemental item。Root trust 丢失后不得为 cleanup 重遍历不可信 namespace；Root handle close API 报错本身不产生新 cause，ADR 0099 后置条件无法证明时保持矩阵外。

Answer Writer gate 只信 Windows mutex operation，并使用 non-alertable zero-time wait。无法建立、打开或等待该数据根的 ownership mechanism，包括 zero-wait 返回 `WAIT_FAILED` 或其他未批准返回值，选择 `answer_writer_coordination_unavailable`；zero-wait 精确返回 `WAIT_TIMEOUT` 才选择 `answer_writer_busy`。`WAIT_OBJECT_0` 与 `WAIT_ABANDONED` 都表示当前编排线程取得 depth 一 ownership，并且都进入每次 ask 的完整持锁 orphan scan；后者只说明前 owner 异常消失，不证明一定存在 orphan，也不能产生 blocked primary。所有 descendant operation/handle settle 且 no-commit 本地证据已冻结后，取得 ownership 的同一编排线程必须成功 `ReleaseMutex` 一次，再关闭 mutex handle，最后关闭 Data Root anchor；未取得 ownership 的 timeout/failure 路径不得 release，但 create/open 已经返回的任何有效 mutex handle 仍必须关闭，create/open 本身失败时才没有 handle。Handle close/release API 报错本身不产生第八项 failed cause；ADR 0099 的权威后置条件成立时按 ADR 0097 仲裁现有候选，无法证明时保持矩阵外。PID、时间戳、lock file、owner metadata 或 staging 年龄不得制造 busy。

Busy 不等待、不排队、不内部重试、不生成 `answer_id`，也不运行后续 gate。成功取得 ownership 后，单个历史 orphan 无效、冲突或补交失败必须保持现场且只可成为以后批准的 supplemental，不能阻止当前 ask；但 staging 集合无法安全枚举、扫描协议无法成立等全局 orphan-scan 基础设施故障不能静默继续，已由 ADR 0095 归入 no-commit `failed`，并按 ADR 0097 参与跨 outcome 仲裁。取得 ownership 后的本次 staging/Answer 形成、manifest、rename 或其他提交故障也不再归入这两个 coordination cause。

十一项 blocked cause 的全局相对仲裁固定为串行 fail-fast：

~~~text
RawArgvPreflightV1（project-wide，本矩阵外；ceiling、verdict、presentation 与 exit 已冻结）
→ PASS 后 lazy-import Typer / Rich / 完整 command graph（本矩阵外）
→ Typer grammar / parser（本矩阵外）
→ Question validation
→ configuration validation + in-memory safe projection
→ provenance formation
→ Data Root safe open + physical identity
→ zero-wait Answer Writer ownership
→ under-lock orphan scan / recovery
→ atomic cancellation-or-answer_id cutover
~~~

只要 invocation 仍处于可继续执行状态，每个 blocked gate 就只有在前一 gate 成功后才运行；第一个权威 blocked cause 一经选择便停止全部后续 blocked probe，禁止并行 collect-all、按线程完成顺序或异常到达时间挑选 primary。Provenance 位于 mutex 之前，避免在 Git 查询期间占有 writer ownership，也保证 provenance-blocked invocation 不触发 orphan recovery 副作用；所以 busy 的“立即”仅表示 invocation 抵达 mutex gate 并观察到 `WAIT_TIMEOUT` 后立即停止，不是压过 Question、Configuration、Provenance 或 Data Root 的全局优先级。

ADR 0098 的 atomic pre-ID barrier 是同一个 command-owned 串行状态转换对 cancellation latch 的权威 snapshot 与规范 `ans_<UUIDv4>` ID 的成功生成、验证、锁存，不是“先 final check、后 generate ID”两个步骤；取消先赢则绝不安装 ID，预生成 UUID bytes 也不算 identity，ID 先赢则 Answer 生命周期不可逆开始。该 latch 还在 handled adapter 入口、每个 gate 进入前与返回后、enumeration 与相邻 orphan candidate/recovery 等安全有界单元之间，以及任何 no-commit outcome 最终锁存前由唯一编排器消费；cancellation transition 与下一项新工作的 commitment 必须串行二选一，取消先赢后不再运行后续 blocked probe 或其他业务工作。ADR 0097 已冻结 global failed、ID 前 provisional interruption 与 provisional blocked 同时存在时按 `failed > interrupted > blocked` 仲裁；本 ADR 的顺序只决定 invocation 仍继续时多个 blocked condition 的相对选择，旧 orphan 即使在本次持锁扫描中完成 rename 也不是当前 invocation 的 commit。Cutover 不是 staging 创建、`started_at` 采集或最终 rename；ID 后取消必须按 ADR 0093 尝试提交 interrupted Answer，不能退回 pre-ID no-commit interruption。Barrier 内 UUID 生成/验证失败不得冒充 `pre_answer_formation_failed`，当前无获准 cause 时保持矩阵外。

Leaf validator 只返回上列封闭 cause；command-owned blocked classifier 将一个 cause 一对一映射为一个 primary variant。异常类型/text、Win32 code、内部阶段名、路径与运行时字符串都不能参与 code 构造。`.v1` 的 machine 语义、primary-only 角色、`blocked` outcome 与空 context 一经发布不得静默重解释；不兼容变化必须使用新的 versioned code。

本 ADR 只冻结十一项 blocked cause 之间的相对选择；跨 outcome 静态优先级已经由 ADR 0097 冻结为 `failed > interrupted > blocked`，cancellation latch/checkpoints、stop-new-work 与原子 Answer identity cutover 已由 ADR 0098 冻结，完整 drain、typed cleanup/close/release、安全后置条件与不安全 teardown 的矩阵外边界已由 ADR 0099 冻结，`knowledge.ask` JSON stdout cap/buffer 已由 ADR 0107 冻结，可控 JSON presentation failure exit 已由 ADR 0108 冻结，project-wide pre-Typer argv preflight seam 与职责已由 ADR 0110 冻结，PASS 后才 lazy-import CLI framework/command graph 的强入口边界已由 ADR 0111 冻结，唯一 immutable snapshot、Typer exact feed-through 与关闭 shell completion 已由 ADR 0113 冻结，argv0 计量排除已由 ADR 0114 冻结，三个 raw suffix ceiling、`len(str)` 单位、精确 aggregate 与 inclusive 边界已由 ADR 0115 冻结，RawArgvPreflight resource violation 的无 payload 分类、dimension non-disclosure、固定 stderr、empty stdout 与 exit `2` 已由 [ADR 0116](./0116-return-2-with-one-fixed-stderr-line-for-raw-argv-resource-violation.md) 冻结。No-commit `failed` 与 `interrupted` primary 已分别由 ADR 0095、ADR 0096 闭合；orphan/capture/maintenance supplemental variants、Human 中文文案与 exit、其余 CLI parser/bootstrap/internal/argument/presentation failure exit 和任何持久诊断资产仍待冻结。
