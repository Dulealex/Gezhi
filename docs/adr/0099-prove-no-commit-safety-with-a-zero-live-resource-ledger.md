# 以清零活跃资源台账证明 no-commit 安全边界

`knowledge.ask` 只有在 ADR 0094 的 gate stop condition、ADR 0097 的 terminal-cause arbitration 或 ADR 0098 的 cancellation transition 已于同一 command-owned commitment domain 锁存 stop-new-work 后，才能进入 `NoCommitSafeBoundaryV1`。唯一 Knowledge 编排器拥有封闭的 command-owned typed live-resource ledger：每项 gate、orphan candidate/recovery、业务或 I/O operation、worker、collector、monitor、operation-owned callback、子进程、Job、pipe、pending I/O、扫描/文件/目录/mutex/Data Root handle 与 mutex ownership，都必须先以 commitment 登记再启动；operation 返回的新资源必须在同一条 ledger entry 中从 in-flight 转成 owned，不能出现未登记窗口。只有权威 completion 已取得、相关执行单元已 join 或静止，且以后不可能再触碰本 invocation 状态或 namespace 时，条目才算 settled；stop/cancel request、timeout、`TerminateJobObject` 返回、观察到进程退出、发起 close 或关闭一个 handle 本身都不是 settle。Codex Job、capture 与 overlapped I/O 继续服从各自更强的既有 finalization boundary，本决策不承诺任何同步 Win32 调用都能有界取消。

Stop-new-work 后，编排器排空所有已登记 operation，先在仍持有 ownership 时冻结 no-commit cause、commit/target 结论及之后仲裁所需的本地不可变证据，再按 child-before-parent 顺序关闭具体类型的 scan enumerator、candidate/recovery、文件与目录资源。取得 mutex ownership（包括 `WAIT_ABANDONED`）时，必须由取得它的同一编排线程在 ownership depth 精确为一时成功执行一次 `ReleaseMutex`，随后关闭 mutex handle；未取得 ownership 时不得 release，但 create/open 已返回的有效 handle 仍须关闭。Data Root anchor 保持到全部 descendant operation/handle 已 settle 且 mutex 已释放并关闭后，最后关闭；root trust 已丢失时不得为了证明 cleanup 再遍历不可信 namespace，也不得从 raw configured path 重开 root。释放 ownership 后不得再访问 root/staging；另一 writer 随后恢复历史或本次 staging 不改变已经冻结的 invocation-local no-commit 事实。

没有锁存 `answer_id` 时，只须证明本 invocation 从未建立自己的新 Answer staging、target、asset、Codex Job 或 capture resource；已完成的旧 orphan recovery 是旧 Answer 的确定结果，不回滚也不构成本次 commit。已经锁存 ID 但本次没有 commit 时，必须证明 non-replacing rename 未成功、expected target 不是本 invocation 的 commit、没有 pending 或结果不明的 rename、全部 Answer I/O 已停止且 staging 没有 live handle；staging 只可原地静止保留在 `answers/.staging/` 并继续被正式 reader 忽略，不得为了收尾移动、删除、修补或伪装成 quarantine。Target conflict 允许既有 target 存在，但必须证明它不是本次 commit。持久 staging entry 与已经提交的旧 orphan 不是 live-resource ledger 条目。

只有 command-owned mutation 已静止、全部适用 live-resource 条目清零、commit/target 状态确定且上述 namespace 后置条件成立后，ADR 0097 的 arbiter 才可锁存最终 no-commit outcome。Cleanup、close 或 release API 报错必须先服从 ADR 0095 已有七项 cause 的完整谓词；报错本身不新增第八项 `failed`，若仍有独立权威证据证明安全后置条件则按既有候选仲裁。V1 对 `ReleaseMutex`、`CloseHandle`、`FindClose` 失败没有替代证明，也不得重试或猜测可能已经成功的 release/close；进程树、worker/callback、pending I/O、句柄、ownership、rename/commit、target identity 或 staging isolation 任一项无法证明时，路径位于正常矩阵外，不形成正常 envelope、normal-return exit 或第四种 outcome。本 ledger 仍不接管 cancellation profile；ADR 0100 与 [ADR 0104](./0104-continue-with-a-no-source-cancellation-profile-when-capability-is-absent.md) 分别用独立的 profile-specific zero-in-flight、source release 与 presentation cutover 管理它，本决策只约束可能继续触碰业务、I/O、root、staging、Job 或 capture 的执行单元。
