# 让 command-owned child 在无控制台环境中运行

Knowledge v1 把本决策作为 Literature 与未来 Bot 共用的 Windows Codex attempt launcher 基线：每个 semantic attempt 的 root 都由 Gezhi 编排器直接执行一次 `CreateProcessW`，目标是项目 npm runtime 中已锁定并验证的唯一 x64 native `codex.exe`。该文件是项目级 Codex CLI 的原生实现，不是桌面应用 WindowsApps 随附 CLI，也不是用户级 npm CLI。`tools/codex.ps1` 只保留为安装验收与人工项目入口，不得成为 runtime attempt 的 PowerShell wrapper；attempt 不得使用 `shell=True`、`cmd.exe`、PowerShell、`ShellExecute`、文件关联、`.cmd` 或临时 wrapper 启动真正的 Codex，也不得在内部先运行一次 `codex.exe --version` 再隐式创建第二个进程。

每个 semantic invocation 在首次 launch commitment 前恰好运行一次项目自有 runtime resolver，并把结果粘性冻结给本 invocation 的全部 attempts。Resolver 必须联合验证：`runtimes/codex/package.json` 根依赖为 `"@openai/codex":"0.146.0"`；`runtimes/codex/package-lock.json` 的 main node、`@openai/codex-win32-x64` alias/optional-dependency node、各自 version 与 integrity 都与锁文件闭合；installed main/native package 的 `name` 都精确为 `@openai/codex`，version 分别为 `0.146.0` 与 `0.146.0-win32-x64`。从受信任项目根到 `runtimes/codex/node_modules/@openai/codex-win32-x64`、其后目录链与唯一 `codex.exe` leaf 都不得含 reparse point；leaf 必须是闭合在该 native package root 内的普通文件，候选恰好一个。`CreateProcessW.lpApplicationName` 必须为该冻结的非空绝对路径，`lpCommandLine` 只从冻结 argv 以项目 Windows quoting 构造，不得令 `lpApplicationName=NULL` 或经 PATH/App Paths 搜索。

Metadata、integrity、reparse、closure、唯一性、路径或 quoting proof 失败时在 commitment 前阻塞语义阶段且 `attempts=[]`，不得启动版本探针、PowerShell wrapper、全局/桌面 CLI 或第二套 resolver 作为回退。V1 把通过 proof 的项目 runtime subtree 视为本 invocation 期间可信且不可变的本地 trust root；并发替换属于 supported baseline 外，Gezhi 不声称用 `CreateProcessW` 路径参数阻止外部篡改。首次 proof 后不得为重试重新枚举或改选 CLI；原冻结路径后来启动失败只进入既有 attempt process-failure 规则。实际 `--version`、登录与非交互 smoke 验收属于环境配置/`doctor` 边界，不是每个业务 attempt 的隐藏 child；runtime resolver 与 `tools/codex.ps1` 消费相同项目锁定身份，并由合同测试防止漂移。

每次 semantic attempt root 创建必须包含 `CREATE_SUSPENDED | CREATE_NO_WINDOW | EXTENDED_STARTUPINFO_PRESENT | CREATE_UNICODE_ENVIRONMENT`，并且不得包含 `CREATE_NEW_CONSOLE`、`DETACHED_PROCESS`、`CREATE_NEW_PROCESS_GROUP` 或 `CREATE_BREAKAWAY_FROM_JOB`。这里的 command-owned child 精确指 Gezhi 编排器直接创建并拥有的 attempt root；锁定 Codex CLI 自己创建的后代是 provider-runtime descendants，不被虚构为第二批 orchestrator-owned roots。`CREATE_NO_WINDOW` 只约束这次直接创建的 console process，不被夸大成可继承的安全策略；普通后代留在同一 Job，但 V1 不声称能阻止不受信任后代显式调用 `AllocConsole`、`AttachConsole`、`CREATE_NEW_CONSOLE`，也不把 Job Object 当作 console sandbox。锁定 runtime 及其后代不得主动创建或附着 Gezhi console，这一项属于 Windows 验收基线。其他非 Codex command 类型只有先冻结自己的精确 stdio/生命周期 profile 后，才能复用本 ADR 的 no-console、handle allowlist 与 Job 模式。

`STARTUPINFOEXW.cb` 必须正确，`dwFlags` 必须包含 `STARTF_USESTDHANDLES`，三项标准句柄冻结为唯一映射：stdin 是 child-read 的单向 pipe，向 `codex exec -` 传入本 attempt 已冻结的 exact immutable prompt bytes；stdout 是 child-write 的独立 events pipe，由 collector 原样形成 `events.jsonl`；stderr 是 child-write 的 `NUL` handle，不捕获、不解析、不持久化，也不参与 failure 分类。`--output-last-message` 的 fresh writer-private file 仍是 `final_message.txt` 的唯一来源，不属于标准流。Stdin writer 与 stdout collector 必须在 resume 前准备完成；成功 resume 后 writer 才写入完整 prompt，完成或 stop 时关闭父侧 stdin-write 以表示 EOF，stdout collector 从运行期持续读取到 EOF。不得把 Question/prompt 放入 argv，也不得把父 console 的任一标准句柄传给 child。

创建必须使用 `PROC_THREAD_ATTRIBUTE_HANDLE_LIST`，`bInheritHandles=TRUE`，且 allowlist 恰好只含 `{stdin-read, stdout-write, stderr-NUL}` 三个有效、方向正确且可继承的 child-side handle。父侧 `stdin-write`、`stdout-read` 必须不可继承；Job、process/thread、Data Root、staging、mutex、cancellation bridge 及其他所有 handle 也必须不可继承且不在列表中。`CreateProcessW` 返回后，父进程立即关闭自己持有的三项 child-side duplicate，只保留已登记的父侧 endpoints 与控制 handle；任何成功、失败、取消或 stop 分支都必须按同一 ownership ledger 收敛。否则句柄泄漏可能阻止 stdout EOF，不能形成安全终态。

每个 attempt 在创建 root 前建立独占、unnamed、不可继承的 Windows Job Object，启用 `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`，且不启用 `BREAKAWAY_OK` 或 `SILENT_BREAKAWAY_OK`。唯一启动顺序为：准备 pipes/NUL、extended startup attribute 与 collectors；以 suspended/no-window profile 直接创建已解析的 native Codex CLI root；用 `AssignProcessToJobObject` 将 root 加入该 Job；关闭父进程的 child-side duplicates；最后只在 `ResumeThread` 返回 previous suspend count 精确为 `1` 时承认 provider 已开始。不得同时使用 `PROC_THREAD_ATTRIBUTE_JOB_LIST` 建立第二条 assignment 路径。父进程处于外层 Job 时仍必须证明 nested assignment 合法并成功，不能用 breakaway 或无 Job 运行作为降级。

`CreateProcessW` 前任一 flag、attribute、stdio、路径或 ownership proof 失败时不得启动。创建成功而 Job assignment 失败时，root 仍应保持 suspended，编排器必须直接终止并等待该 root signaled，再关闭和结清资源；不得因空 attempt Job 而误称整个 root 已静止。Assignment 成功后 resume 失败、返回 `0`、大于 `1` 或结果不确定时按“可能已经运行”处理，通过 attempt Job 请求停止整棵树并完成既有机械排空。任何情况下都不得无 Job resume、重新用普通 launch 尝试，或把一次失败拆成第二次隐式进程启动。

父进程 Ctrl+C 只能通过 ADR 0098–ADR 0105 已冻结的 Gezhi bridge/latch 影响编排器；Codex attempt root 不加入新 process group，也不接收由 Gezhi 生成的 console control event。正常 timeout/cancel/overflow stop 只在仍保有 Job handle 时调用 `TerminateJobObject`，不调用 `GenerateConsoleCtrlEvent`、不按 PID 模拟信号，也不以关闭最后一个 Job handle 作为正常 stop primitive。编排器必须保留 Job handle，直到 root signaled、Job `ActiveProcesses=0`、stdout EOF、final source 复验、writers/collectors/monitor join，以及除 Job-handle entry 外的相关 ledger entries 全部 settled 已经证明；随后才关闭 Job handle并证明 `CloseHandle`/ownership，settle 最后的 Job entry，最终令总 ledger 为零。`KILL_ON_JOB_CLOSE` 只是在 owner 异常退出或最终清理时的 fail-safe，不是 terminal proof。Job handle 意外提前关闭或最终 close/ownership 无法证明时，本 attempt 保持正常矩阵外。

`TerminateJobObject` 的返回、Job fail-safe close、root exit DWORD、后代退出或数值偶合 `130` 都不能反向写 cancellation latch、生成 `interrupted` 或令 Gezhi normal-return `130`；有无父 cancellation observation 仍只按既有时序仲裁。单独 root exit、Job API 成功或 handle close 都不够，正常 stop 必须收敛到上一段完整安全边界。

本决策只冻结 console/process-group 隔离、标准流、handle inheritance 与 Job handoff，不增加 CLI JSON/Human 字段、diagnostic、Answer/manifest/provenance/configuration、日志/trace/telemetry、第三方依赖或新 runtime。Launch/lifecycle 独立失败仍仅在既有 capture-finalization 与 cause 规则能够证明时形成 `process_error`；无法证明安全收尾时保持正常矩阵外。Pipe buffer/chunk 大小、同步或 overlapped I/O、completion port/polling、`TerminateJobObject` 内部退出 DWORD 与 supplemental diagnostic 继续由后续决策冻结；[ADR 0107](./0107-seal-one-bounded-immutable-knowledge-ask-json-buffer.md) 的 CLI JSON stdout cap 和 [ADR 0108](./0108-return-1-for-controlled-knowledge-ask-json-presentation-failure.md) 的 CLI presentation failure exit 都与本 ADR 的 provider-attempt stdout capture/lifecycle 正交，不能反向分类 child failure。

Win32 语义依据见 [Process Creation Flags](https://learn.microsoft.com/en-us/windows/win32/procthread/process-creation-flags)、[UpdateProcThreadAttribute](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-updateprocthreadattribute)、[Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)、[AssignProcessToJobObject](https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-assignprocesstojobobject) 与 [ResumeThread](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-resumethread)。
