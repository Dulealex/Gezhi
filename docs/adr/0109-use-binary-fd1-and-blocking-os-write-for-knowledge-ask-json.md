# 用 binary fd 1 和同步阻塞 os.write 发布 knowledge.ask JSON

`(gezhi.cli_result.v1, knowledge.ask)` 的 handled `--json` path 只在 [ADR 0107](./0107-seal-one-bounded-immutable-knowledge-ask-json-buffer.md) 的 `READY_BYTES` candidate 已以 matching token 成功 seal、所选 cancellation profile 已完成 zero-in-flight 与 source-specific release proof 并进入 `RELEASED` 后，使用本 ADR 的 `WindowsKnowledgeAskJsonStdoutV1`。`NO_OUTPUT_PRESENTATION_FAILURE` 不建立 view、不调用 stdout setup/write，进入 `RELEASED` 后直接按 [ADR 0108](./0108-return-1-for-controlled-knowledge-ask-json-presentation-failure.md) `os._exit(1)`。本 primitive 不被 Human、Literature、其他命令、未来 Bot、GUI、daemon 或同一进程内的重复 invocation 静默复用；[ADR 0116](./0116-return-2-with-one-fixed-stderr-line-for-raw-argv-resource-violation.md) 的 pre-command fd2 presenter 是独立 primitive，不继承本 fd1 buffer、release proof 或 `os._exit(1)` 语义。

在任何 stdout 状态变更前，唯一主编排线程先重新证明 pending slot 仍强引用同一个 authoritative object、`type(buffer) is bytes`、`type(byte_length) is int`（`bool` 与自定义数值类型均不合格）、`byte_length == len(buffer)`、`1 <= byte_length <= 65_536` 且末 byte 为 `0x0A`，再恰好一次建立 `base_view = memoryview(buffer)`。该 view 必须天然满足 `base_view.obj is buffer`、`base_view.nbytes == byte_length`、read-only、one-dimensional、C-contiguous、`itemsize == 1`、`format == "B"`，是同一 `bytes` 的零拷贝视图；不得 cast、复制、重编码或用另一个 bytes-like object 替代。构造或不变量检查抛出的 `MemoryError`、`TypeError`、`ValueError`、`AssertionError` 或其他非本 ADR I/O failure 发生在 mode change 前，按 ADR 0108 的排除规则原样逃逸，不能捕获成 presentation exit `1`。Authoritative `bytes` 与 `base_view` 必须保持强引用直到完整写出、ADR 0108 hard fail-stop 或外部实际终止。[CPython 3.11 `os.write` 实现](https://github.com/python/cpython/blob/v3.11.15/Modules/posixmodule.c#L9267-L9281) 要求传入 C-contiguous bytes-like buffer，本 ADR 进一步把可接受对象收窄为上述同一 `bytes` 的 view。

上述 handled JSON path 从进程启动到此点不得执行任何 stdout write，也不得在 `sys.stdout`、其 wrapper/buffer、CRT stream 或其他用户态层留下待 flush bytes；fd `1` 必须仍是本进程启动时取得的 CRT stdout binding，从未被 close、dup/dup2、rebind、reopen 或另一次 mode change。除唯一主编排线程外，不得存在持有或可能晚触碰该 binding 的 worker/thread/task、子进程可写副本、stdout-emitting `atexit`/finalizer 或其他 writer；ADR 0106 的 Codex child 只能使用自己的 dedicated stdout pipe。任一前置事实无法证明时保持正常矩阵外，禁止用 flush、等待猜测或重绑 fd 抢救。

V1 支持的 fd `1` endpoint 仅限：正常 CPython console stdout、以同步方式打开的普通文件，以及 shell/`subprocess` 建立的同步 anonymous blocking byte pipe。这是 launcher/environment 必须提供并由调用边界证明的 support-profile 前置条件；adapter 不靠一次试写、`isatty`、handle 查询或其他 runtime probe 推断它。`FILE_FLAG_OVERLAPPED` handle、socket、message-mode 或 exotic device、closed/reused/rebound fd `1`，以及任何并发 close/dup/write 都在支持范围外。[Win32 `WriteFile` 契约](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-writefile) 区分同步与 overlapped handle；本 ADR 不创建或管理 overlapped request。

随后唯一 writer 对固定 CRT stdout file descriptor `1` 恰好调用一次 `msvcrt.setmode(1, os.O_BINARY)`。Production assembly 必须直接绑定 CPython 标准库的 `msvcrt.setmode` 与 `os.write`；adapter 的生产接口不接收 callback、wrapper 或可替换 writer，monkeypatch 后的同名对象不属于受支持生产配置。`OSError` catch region 只能包住这一条 `setmode` 调用本身：调用参数准备、前置验证和返回值处理全部在 catch 外。调用正常返回就表示 binary setup 完成，其 previous-mode 返回值只在本地丢弃，不记录、不分支、不恢复；直接抛出的 `OSError` 及其子类是 ADR 0108 的 completed setup failure。除此之外不得捕获 `Exception`/`BaseException`，也不得调用 `sys.stdout.fileno()`、`msvcrt.get_osfhandle`、`os.fdopen`、`dup`、`close`、reopen 或 `WriteFile` 来发现、替换或绕过 fd `1`。[Python 3.11 `msvcrt.setmode`](https://docs.python.org/3.11/library/msvcrt.html#msvcrt.setmode) 把 `os.O_BINARY` 定义为关闭 fd 换行翻译；[MSVC `_setmode`](https://learn.microsoft.com/en-us/cpp/c-runtime-library/reference/setmode?view=msvc-170) 进一步说明 mode 应在该 stream 首次 I/O 前设置，未发生先前写入时无需 flush。不得以 ctypes CRT 调用替换 CPython 标准库 binding。

Binary setup 成功后，writer 固定 `offset = 0` 并只运行下列同步 loop：

~~~text
offset = 0
while offset < byte_length:
    remaining = byte_length - offset
    current_view = base_view[offset:]
    requested = len(current_view)
    validate_current_view_and_requested()
    try:
        count = os.write(1, current_view)
    except OSError:
        adr_0108_hard_fail_stop()
    validate_count()
    offset = checked_add(offset, count)
~~~

Loop 只在 `offset < byte_length` 时进入，因此永不提交 zero-length view。每次调用前都必须在 `try` 外证明 `requested == remaining`、`1 <= requested <= 65_536`、`current_view.obj is buffer`、`current_view.nbytes == remaining`，且 current view 仍是 read-only、one-dimensional、C-contiguous、`itemsize == 1`、`format == "B"` 的同一 buffer zero-copy suffix；不得形成 `buffer[offset:]` bytes 副本。每个 `OSError` catch region 只能包住一条实际的 `os.write(1, current_view)` 调用；view 构造、切片、`len`、所有验证及 checked addition 均在 catch 外。只有 `type(count) is int` 且 `1 <= count <= requested` 才成功；`count < requested` 是已完成的合法 short write，下一轮从新 offset 请求新的全部 remaining，不算 adapter retry，也不得假定固定调用次数。`bool`、其他非 `int`、`count <= 0` 或 `count > requested` 命中 ADR 0108 的 invalid-count hard fail-stop。`os.write` 直接抛出的任何 `OSError` 及其子类——包括 `BrokenPipeError`、`BlockingIOError` 与向上暴露的 `InterruptedError`——都在调用边界被视为 completed I/O failure；adapter 无法也不得按异常来源、`characters_written`、`errno/winerror` 或推测的 signal 因果细分。其他异常与 view-slice 构造失败原样逃逸，不得由广泛 catch 翻译。[Python 3.11 `os.write`](https://docs.python.org/3.11/library/os.html#os.write) 返回实际写入 byte count，并在 system call 被中断且 handler 正常返回时自行重试；这个 primitive-internal 行为不是 Gezhi retry。受支持的 project/prior/default handler 不得从该调用抛出 `OSError`；若外部自定义 handler 违反这一边界，其 `OSError` 无法与底层 I/O failure 区分并仍按调用边界规则进入 ADR 0108，只有非 `OSError` handler 异常保留原异常语义。

本 ADR 所称“同步阻塞”描述受支持 launcher/environment profile 以及 Gezhi 自己不请求 nonblocking 的选择，不表示 adapter 会探测或修复继承状态。它不调用 `os.set_blocking`，也不使用 poll/select、timeout、deadline、sleep/backoff、第二 writer、worker/thread/task、overlapped I/O、IOCP、background completion 或 cancelable wrapper；若范围外的继承配置令 `os.write` 返回 `BlockingIOError`，即按上述 `OSError` 规则进入 ADR 0108，不等待也不重试。受支持的下游 pipe/console/file 不消费时，`os.write` 可以无限期阻塞，直到下游恢复或进程被外部/default/runtime 语义终止；V1 明确接受这个 liveness 代价，不能为了 presentation timeout 引入 pending completion 不确定性。Windows binary console path 在 CPython 3.11 内部会把大于 `32_767` bytes 的 request 截为至多 `32_767` bytes 后执行并返回 completed short write，因此 `65_536`-byte payload 至少需要三次成功调用；更一般的 endpoint 仍可能产生更多合法 partial counts，writer 只信实际 count。[CPython 3.11 Windows write 实现](https://github.com/python/cpython/blob/v3.11.15/Python/fileutils.c#L1675-L1768) 记录了 console cap、GIL release 与 CRT `write` 路径。外部终止仍保留真实 OS/runtime 语义；只有同步调用实际返回获准 completed failure 后，ADR 0108 才能选择 `os._exit(1)`。

`--json` 的规范对象是 authoritative UTF-8 byte sequence，不是 Windows console 上的字形。Stdout 重定向到 pipe 或普通文件时，调用方可以验证 exact bytes；真实 TTY 在 output code page 不是 UTF-8 时可能错误显示 `ensure_ascii=False` payload 中的中文或其他 non-ASCII 字符，因此 console visual rendering 只作 best-effort，不构成 machine acknowledgment 或本 ADR 的正确性承诺。Direct `os.write` 不使用 [PEP 528](https://peps.python.org/pep-0528/) 为 `sys.stdout` 引入的 `WindowsConsoleIO`/`WriteConsoleW` Unicode console 路径；[Microsoft console code-page 文档](https://learn.microsoft.com/en-us/windows/console/console-code-pages) 也说明 byte-to-glyph 解释受 output code page 影响。Adapter 不调用 `isatty` 建立第二分支，不改变 console output code page，也不回退 `WriteConsoleW`/`WindowsConsoleIO`；交互阅读应使用 Human mode，机器消费应重定向 stdout。

只有 `offset == byte_length`、因此 authoritative buffer 连同末尾 LF 已全部被同步 primitive 接受时，presentation 才完成并进入既有 business outcome-to-exit table。一次成功 `os.write` 只证明其返回 count 对应的 bytes 已被同步调用边界接受，不证明下游 reader 已消费，也不证明普通文件数据已落盘；V1 明确不提供 downstream-consumption 或 durability acknowledgment。这里“无 pending operation”只表示 Gezhi 没有建立用户态/background/overlapped outstanding write，不能扩张为对 OS、设备、reader 或持久介质状态的断言。Writer 成功或失败后都不显式 flush、fsync、恢复 text mode、close/reopen fd `1` 或追加任何 bytes；failure 立即服从 ADR 0108，success 沿 one-shot CLI 的 normal handled return 结束。`sys.stdout`/`print`/`sys.stdout.buffer`/`sys.stdout.raw`、`msvcrt.putch`、ctypes/Win32 `WriteFile` 与任何 stdout-emitting `atexit`/finalizer 均禁止；普通解释器 shutdown 即使检查空 wrapper，也不得有项目自有 pending bytes 可写。因为 binary mode 不恢复且 fd `1` 是进程级 CRT 状态，测试必须在独立子进程验证 stdout bytes/exit，不得在测试 runner 或可复用宿主进程内直接调用本 adapter。

Contract tests 至少覆盖：`NO_OUTPUT_PRESENTATION_FAILURE` 在零 view/零 `setmode`/零 write 后 silent exit `1`；`setmode` 恰好一次、成功、`OSError` 与不恢复 mode；单次完整写和多次 short write 的 suffix identity；`bool`/`None`/`0`/负数/大于 requested 的 invalid count；直接 `OSError` 子类与非 `OSError` 异常的不同语义；完整 LF acknowledgment 后 business `0/2/1/130` mapping；Windows 子进程重定向到 pipe/普通文件时 exact UTF-8、单 LF、无 CRLF 翻译；closed stdout 或 reader 提前关闭时 silent exit `1` 且 stderr empty；slow/non-reader 只能由测试 harness 外部终止，adapter 自身不得 timeout；以及没有 print/flush/close/rebind/second writer。测试 double 只能在 test-only harness 中模拟同一个 synchronous、call-completed、no-Gezhi-pending 契约，不得改变 production binding 或把 async completion 冒充合法返回。

该选择用可能无界阻塞与 one-shot process 限制，换取一个无第二 Gezhi 用户态 stdout buffer、无 Gezhi-owned/background/overlapped pending write、可按返回 count 线性推进且能直接满足 ADR 0108 completion proof 的 Windows primitive。它不增加依赖、配置、CLI 字段、diagnostic、日志、持久资产、模型调用或业务 outcome；ADR 0116 已独立冻结 raw argv resource failure 的 fd2/return-`2` contract，本 ADR 仍不冻结其余 parser/bootstrap/internal/argument、Human presentation、supplemental/persistent diagnostics 或其他 command 的 stdout 策略。
