# 为 Knowledge attempt capture 固定逐文件 byte cap

Knowledge v1 对每个 launch-committed attempt 的两项正式 capture 资产分别使用 role-owned contract constant：`attempts/NN/events.jsonl` 的逻辑 `byte_length` 必须在 `0..16777216`，即至多 `16,777,216 bytes = 16 MiB`；`attempts/NN/final_message.txt` 必须在 `0..1048576`，即至多 `1,048,576 bytes = 1 MiB`。两个上限都包含端点：长度恰等于各自 cap 合法，只有确认存在第 `cap + 1` 个 byte、也就是逻辑长度大于 cap，才满足 capture overflow 谓词。两项额度逐文件、逐 attempt 独立，不得互借；每个 attempt 因此最多提交 `17,825,792 bytes = 17 MiB` capture，最多三个 attempts 的单个 terminal Answer 最多提交 `53,477,376 bytes = 51 MiB` capture。`51 MiB` 只是固定双文件与三次 attempt 上限的算术推论，不是第三个可配置或可借用的 aggregate quota，也不是整个 Answer 的大小上限；它不包含根级业务资产、`manifest.json`、writer-private spool、orphan staging、历史 Answer 累计、NTFS 分配簇或其他物理文件系统开销，保证范围继续以 ADR 0076 为准。

这些 cap 由版本化 `knowledge_answerer_v1` 合同拥有，不进入 `effective_config.json`，不增加 manifest 顶层、attempt item、asset item、marker 或 sidecar 字段；`manifest.assets[*].byte_length` 仍只记录对应正式资产的实际逻辑长度，validator 依据本合同常量复验。两项路径专属范围都与 ADR 0085 的通用 `0..9223372036854775807` 范围取交集并优先，后者绝不把 capture cap 抬高；既有包含端点、`cap + 1` witness、exact-prefix retention、usage 与终态分类不变。`final_message.txt` 的 `1 MiB` retention cap 不替代 eligible final 已有的 `65536-byte` Answer validation budget：`65,537..1,048,576` bytes 仍不是 retention overflow，但 eligible final 继续得到既有 `answer_output_invalid`。本决策只冻结数值、逐文件归属和包含边界；overflow 的 exact-prefix retention 由 ADR 0078 冻结，witness、Job stop 与 mechanical drain 由 ADR 0079 冻结，failure class、顶层 code/stage、最高优先级与不重试由 ADR 0080 冻结。ADR 0081 只为 usage 可复验性增加全局保守门禁：events 正式长度恰为 cap 时四项 token 全为 `null` 且 `usage_unavailable=true`，低于 cap 时才运行严格 usage adapter；这不把 exact-cap clean EOF 分类为 overflow。`TerminateJobObject` 内部退出 DWORD 与外部诊断继续后续决定；除 ADR 0078 的 capacity overflow 窄例外外，不授权截断。长度恰等于 cap 仍不能单独证明 overflow。
