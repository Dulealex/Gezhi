# Ctrl+C 能力缺失时以无 source 的取消生命周期继续执行

当 [ADR 0103](./0103-require-a-read-only-conin-processed-input-capability-gate.md) 的 `ConsoleCancellationCapabilityV1` 在 capability handle 已安全关闭并完成 ownership proof 后得到 `capability_absent`，唯一主编排线程必须在任何领域 gate/probe 启动前选择纯逻辑 `NoInteractiveCancellationBridgeV1`；这是 adapter capability fact，不是 Question、配置、Data Root 或其他领域失败。后续 [ADR 0105](./0105-use-the-no-source-profile-when-the-current-process-is-being-debugged.md) 另行授权 `interactive_candidate` 在 pre-registration debugger gate 返回 nonzero 时合法复用同一 profile；这不把 capability 改写为 absent，也不是失败降级。此 profile 不加载 [ADR 0101](./0101-use-a-project-owned-native-win32-ctrl-c-bridge.md) 的项目 DLL，不注册 `HandlerRoutine`，不调用 `SetConsoleCtrlHandler`，也不执行 [ADR 0102](./0102-normalize-inherited-ctrl-c-ignore-before-activation.md) 的 inherited-ignore normalization。ADR 0105 已返回 zero 并选定 native route 后，registration、normalization 或 activation 失败不能重新分类为 `capability_absent`/`debugger_present`，也不能回退到本 profile。

`NoInteractiveCancellationBridgeV1` 复用 [ADR 0100](./0100-seal-the-handled-cancellation-window-before-presentation.md) 的完整状态序列 `OUTSIDE -> ARMED_PASS_THROUGH -> ACCEPTING -> SEALED_PASS_THROUGH -> RELEASED`，但每个状态都携带 invocation-local 的固定证明 `source=none`。`OUTSIDE -> ARMED_PASS_THROUGH` 只建立主线程拥有的逻辑 control state，并证明本 profile 未创建、注册或接入任何能够参加 ADR 0100 admission、写 ADR 0098 latch 的 callback source；该证明不枚举、禁用或否认进程既有的 prior/default/runtime signal source。`ARMED_PASS_THROUGH -> ACCEPTING` 是第一项领域工作前必须完成的纯逻辑 activation。`ACCEPTING` 只保留与 interactive profile 相同的 orchestration seam，不表示存在能够赢得 admission 的 callback。

该 profile 的 cancellation latch 必须从初始化到 `RELEASED` 始终为 unset，`observed_monotonic_ns` 始终不存在，accepted generation 与 accepted-in-flight 固定为零。它不能产生应用级 `interrupted`、`knowledge.ask.user_interrupted_before_answer.v1`、`knowledge.ask.user_interrupted.v1` 或正常 handled-return `130`；既有 `succeeded`、`blocked` 与 `failed` 仲裁不变。若本 profile 观察到 Gezhi-owned native registration/handler pointer、callback admission、非零 generation/in-flight、已设置 latch 或 cancellation observation，说明 profile identity 或状态证明已破坏，路径位于正常矩阵外，不能把该事实重解释为用户中断或能力缺失。

领域执行与适用 safe-finalization 完成后，唯一主编排器必须先在 `ACCEPTING` 中完整构造并验证 candidate immutable `outcome/result/diagnostics` 与该 mode 已批准的 presentation disposition，再于唯一主线程串行转换中锁存 exact triple、disposition 及其完整 payload 并进入 `SEALED_PASS_THROUGH`；不得先 seal 后验证、替换 candidate 或因验证失败回退 phase。[ADR 0107](./0107-seal-one-bounded-immutable-knowledge-ask-json-buffer.md) 已要求 no-source `knowledge.ask --json` 复用 `READY_BYTES | NO_OUTPUT_PRESENTATION_FAILURE` pending union 与一次性 token binding，expected generation 固定为零；正常分支的完整 envelope、exact canonical buffer 与 byte length 必须在逻辑 seal 前形成。此 profile 的 coherent release proof 必须同时成立：`source=none`、无 Gezhi-owned handler pointer/registration/callback epoch、accepted generation 与 accepted-in-flight 均为零、latch unset、observation absent 且 `never_registered=true`；因此 callback drain 为零，matching removal 证明为本 invocation 从未建立 Gezhi-owned registration，两者都不调用 Win32 removal API。证明成立后才进入 `RELEASED` 并开始 JSON/Human presentation。No-source state、seal、candidate identity、零 drain 或 never-registered ownership 任一项无法证明时保持正常矩阵外，不新增 outcome 或 diagnostic。

No-source selection reason（`capability_absent` 或 `debugger_present`）不写入 CLI JSON、Human 输出、Answer、manifest、provenance、配置或其他持久资产，也不产生 supplemental warning。未来 `doctor` 可以用独立的实时检查报告 cancellation capability/debugger state，但不能从本次命令的静默行为反推或持久化该事实。Task Manager、父进程终止、外部 `TerminateProcess`，以及任何实际由 prior/default/runtime 投递的 Ctrl+C、signal 或 `KeyboardInterrupt` 都不属于 Gezhi 的受控 interruption envelope，可能在 presentation 前后留下零输出、前缀、完整输出或直接终止；本 profile 不捕获、修补或映射它们，其进程退出数值即使偶合 `130` 也不是应用级 handled-return `130`。

后续 [ADR 0105](./0105-use-the-no-source-profile-when-the-current-process-is-being-debugged.md) 已冻结 `interactive_candidate` 在当前进程 user-mode debugger present 时静默复用本 profile，并保持 capability 与 selection reason 分离；[ADR 0106](./0106-run-command-owned-children-without-a-console.md) 已冻结与 profile 无关的 orchestrator-owned Codex attempt root console、process-group、stdio/handle 与 Job isolation。
