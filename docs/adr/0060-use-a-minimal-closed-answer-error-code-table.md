# 使用最小封闭的 Answer error code 表

Knowledge v1 的 terminal manifest 只接受 15 个稳定 error code，并把每个 code 静态绑定唯一 `(status, stage)`：既有的 FTS、检索查询、检索物化、View 超限、五类 Codex 瞬时耗尽、未知 Codex 进程失败与 Citation 链接构造 code 保持不变；新增 `codex_runtime_unavailable`、`synthesis_input_invalid`、`answer_output_invalid` 与 `answer_rendering_failed`，分别闭合运行依赖、调用包构造、结构化结果校验及通用确定性渲染的未命名分支。manifest 只保存裸 code，不保存 `blocked:` / `failed:` 前缀；表外值、别名或错误映射均无效，任何表演进都升级 manifest Schema。首版把所有结构化输出校验归并为 `answer_output_invalid`，把链接之外的渲染问题归并为 `answer_rendering_failed`，扩展 `retrieval_materialization_failed` 覆盖四个检索 JSON 资产的形成、确定性序列化、普通文件写入并关闭、哈希与复验失败，并扩展 `codex_process_failed` 覆盖未另行分类的进程生命周期、进程树终止和 provider 事件捕获失败，以牺牲仅看 code 时的细粒度为代价，换取完整覆盖、稳定机器接口和可在首个 Windows 实现中一次穷举验证的最小集合。

ADR 0080 让已通过 capture-finalization 安全门的 confirmed overflow 复用现有 `codex_process_failed`，并固定绑定既有 `(status=failed, stage=synthesis)`；不增加第 16 个 manifest code。Overflow attempt 的 `failure_class=process_error`、不重试与顶层映射来自 ADR 0080 的显式规则，不是实现擅自扩大 catch-all；安全边界无法证明时仍只留 staging。代价是 terminal manifest 不区分 overflow 与其他 process failure，正式资产长度恰等于 cap 也不能单独证明 overflow；ADR 0081 只把该长度用于保守 usage 门禁。ADR 0092 已将 committed `codex_process_failed` 静态映射为 CLI primary `knowledge.ask.codex_process_failed.v1`，但 overflow 专属 supplemental context 继续另行冻结。
