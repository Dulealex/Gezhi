# 冻结未提交 knowledge.ask 的 interrupted 主诊断

当 `command="knowledge.ask"` 已进入 handled path、本次 invocation 没有提交自己的新 Answer，且 no-commit terminal-cause classifier 最终选择 `interrupted` 时，唯一 primary 必须精确为 `{"code":"knowledge.ask.user_interrupted_before_answer.v1","context":{}}`，outer 固定为 `outcome="interrupted"`、`result=null`，完整合法 JSON envelope 沿正常 handled-return 返回时 process exit code 固定为 `130`。该 code 只作 primary，不能用于 committed Answer、blocked、failed 或 supplemental；它不复用 committed-only `knowledge.ask.user_interrupted.v1`，也不披露取消来源、时间、阶段、句柄或内部错误。

该分支要求 ADR 0098 的 command-owned cancellation latch 在原子 pre-ID barrier 先于本次新 `answer_id` cutover 线性化，并且 ADR 0099 的 `NoCommitSafeBoundaryV1` 已证明所有适用 operation、进程、I/O、句柄与 ownership 达到安全收尾点；这些条件只建立合格 provisional interruption，最终没有 ADR 0095 的七项 failed candidate 时才由 ADR 0097 选择本分支。单独观察到 Ctrl+C、Codex attempt `failure_class=interrupted`、子进程退出、Windows 外部强杀或进程消失都不足以选择本码；`answer_id` 一旦成功生成、验证并锁存，安全取消必须尝试提交完整 `status=interrupted` Answer，提交成功走 ADR 0092，terminalization/commit 失败走 ADR 0095 的 no-commit failed union 或正常矩阵外路径。

本决策只冻结 classifier 已经最终选择 `interrupted` 后的一对一 code binding。后续 ADR 0097 已冻结 cancellation 与 provisional blocked/failed 同时存在时按 `failed > interrupted > blocked` 仲裁，ADR 0098 已冻结唯一 Ctrl+C bridge/latch、固定 checkpoints、新工作 commitment、stop-new-work、final no-commit lock 与 atomic pre-ID barrier，ADR 0099 已冻结完整 drain、typed cleanup/close/release 与矩阵外边界；在 `NoCommitSafeBoundaryV1` 前候选 interruption 只能是 provisional cause，不能提前发布 envelope。

ADR 0100 后续进一步要求该 primary 所在的 complete diagnostics 与 final `outcome`、`result` 在 immutable command-state seal 中共同锁存；[ADR 0107](./0107-seal-one-bounded-immutable-knowledge-ask-json-buffer.md) 又要求同一 candidate 锁存 `knowledge.ask --json` 的 presentation disposition 与完整 payload。只有所选 cancellation profile 的 zero-in-flight 与 source-specific release proof 完成并进入 `RELEASED` 后才可 presentation；[ADR 0104](./0104-continue-with-a-no-source-cancellation-profile-when-capability-is-absent.md) 的 no-source profile 永远不能建立该 primary。Seal 后 Ctrl+C 不得新建本码；命中 [ADR 0108](./0108-return-1-for-controlled-knowledge-ask-json-presentation-failure.md) 的权威 completed presentation failure fact 与无 pending 证明时，Gezhi 静默 `os._exit(1)`，不使用本码的应用级 `130`，且不以调用方是否最终观察到完整 envelope 为命中前提；若 exact full buffer（包括 LF）实际到达，receipt 仍成立。External/default 实际终止的数值即使偶合 `130`，也不是本 ADR 的 normal-return `130`。
