# 按终因分类未提交的 knowledge.ask outcome

Final checkpoint 已通过、Root trust 仍成立且 target 不存在时，non-replacing same-volume rename 返回其他失败；只有随后能证明 staging 未提交、target 不是本次 commit 且全部操作安全停止，才以 `{"code":"knowledge.ask.answer_commit_failed.v1","context":{}}` 选择 no-commit `failed`、`result=null` 与正常 JSON exit `1`。禁止自动重试；完整 terminal staging 留给以后 orphan recovery 独立复验。Target-exists 使用 `answer_target_conflict`，root trust loss 使用 `data_root_integrity_lost`。Rename outcome 或 namespace 状态无法确定时，不能在 committed 与 no-commit 之间猜测，仍在正常矩阵外。

本次新 Answer 的 expected target 在 final checkpoint 已存在，或 non-replacing rename 明确返回 target-exists，且 Root trust 仍成立时，使用 `{"code":"knowledge.ask.answer_target_conflict.v1","context":{}}` 选择 no-commit `failed`、`result=null` 与正常 JSON exit `1`。禁止覆盖、删除、合并、比较后复用目标或换新 `answer_id` 重试；本次 staging 原地隔离。目标即使有效且 byte-identical 也不是本次 commit。历史 orphan candidate-local target conflict 仍只作 supplemental；root trust loss 优先，其他 rename failure 使用独立 cause。

本次新 Answer 已进入 terminal `manifest.json` formation 且 Root trust 仍成立时，canonical buffer/cap、direct exclusive-create、write/completion/close、readback、Schema/canonical byte identity、目录闭合或跨资产复验失败，唯一 primary 为 `{"code":"knowledge.ask.answer_manifest_failed.v1","context":{}}`，配 no-commit `failed`、`result=null` 与正常 JSON exit `1`。任何 partial、既存或无效 manifest 保持原 staging bytes，不得删除、修补、重写或 canonicalize。历史 orphan manifest 无效仍只作 supplemental；manifest formation 前的 non-terminal asset failure 使用 `answer_staging_failed`，root trust loss 使用 `data_root_integrity_lost`，target conflict 与 final rename failure 不使用本码。

`answer_id` 已生成且 Root trust 仍成立时，本次 staging 目录无法安全创建、任一 non-terminal asset 无法形成/写完/验证/安装，或 writer-private spool/tail/temp 无法撤销而阻止封闭 terminal asset set，统一使用 `{"code":"knowledge.ask.answer_staging_failed.v1","context":{}}` 选择 no-commit `failed`、`result=null` 与正常 JSON exit `1`；已有 staging 原地隔离。Terminal `manifest.json`、expected target conflict 与最终 directory rename 分别属于后续独立 cause。若同一业务/runtime 故障仍成功提交 terminal `status=failed` Answer，则改走 committed matrix；如果 root trust 丢失，则由 `data_root_integrity_lost` 获胜。无法安全停止 writer/子进程或形成 envelope 时仍在正常矩阵外。

Writer ownership 已取得且 Data Root trust 仍成立时，若整个 `answers/.staging/` 无法安全枚举，或 invocation-wide orphan scan protocol 无法建立/完成，唯一 primary 固定为 `{"code":"knowledge.ask.orphan_scan_failed.v1","context":{}}`，配 no-commit `failed`、`result=null` 与正常 JSON exit `1`。该分支不得生成新 `answer_id`、检索或调用 Codex。单个 orphan 的非法名称、无效 manifest、target conflict 或 candidate-local recovery rename failure 仍只作 supplemental 并继续扫描；若真正丢失 root trust，则改由 `knowledge.ask.data_root_integrity_lost.v1` 获胜。

Caller-owned Question、Configuration 与 Git facts 已合法，但 Answer 身份生成前的 `QuestionEnvelopeV1`、role audit bytes 或 provenance object 无法机械构造/canonical-serialize，统一使用 `{"code":"knowledge.ask.pre_answer_formation_failed.v1","context":{}}` 选择 no-commit `failed`、`result=null` 与正常 JSON exit `1`。三处不拆码，因为调用方处理方式相同；该码不是 internal catch-all，资源耗尽、内部不变量破坏或连诊断 envelope 都无法形成时仍在正常矩阵外。

初始 Data Root gate 成功后，invocation 不得再次选择 Data Root `blocked`。后续持锁 recovery、staging 创建前或最终目录改名前的强制 checkpoint 若无法继续证明 root identity、canonical root、父链或 reparse 状态仍安全且相同，这是当前运行的完整性故障：只要能够安全停止并形成 handled envelope，就选择 no-commit `failed` 与 `result=null`，无论 `answer_id` 是否已生成。该分支唯一 primary 是 `{"code":"knowledge.ask.data_root_integrity_lost.v1","context":{}}`，正常 JSON exit 为 `1`；明确漂移与无法重新建立证明使用同一码。Root 已失去信任时不得为了留下审计而继续写入或提交 terminal `status=failed` Answer；本次 staging 若存在则原地隔离。若 teardown 无法证明安全，仍不进入本 ADR 的正常矩阵。

当 `command="knowledge.ask"` 的本次 invocation 没有成功提交自己的新 Answer 目录时，outer `result` 必须为 `null`，且 handled JSON envelope 的 `outcome` 只能是 `blocked`、`failed` 或 `interrupted`；`succeeded` 与 `result=null` 的组合对 `knowledge.ask` 永远无效。启动扫描中补交旧 orphan Answer 不算本次新 Answer commit，也不能把当前 invocation 提升为 `succeeded` 或产生 result receipt。

无 committed Answer 的终因分类固定为：

| terminal-cause class | required outer `outcome` | normal JSON exit |
|---|---|---:|
| 输入问题或可恢复前置条件阻止本次创建新 Answer | `blocked` | `2` |
| 本地 Answer 形成、验证或目录提交失败 | `failed` | `1` |
| 同一 cancellation latch 在原子 pre-ID barrier 先于本次新 `answer_id` cutover 线性化、能够完成受控安全收尾，且最终没有七项 failed candidate | `interrupted` | `130` |
| 没有新 Answer commit 但命令成功 | 禁止 | 不存在 |

`blocked` 表示调用方改变输入、等待协调条件或修复可恢复前置条件后可以重新发起；已经进入 Knowledge command adapter 后，caller-owned question text 经现有领域规则得到的非法/超限/过复杂 Question 与 Answer writer mutex busy 属于这一类。Adapter 自身构造了错误 shape/type 的 `QuestionEnvelopeV1` value 是内部 invariant failure，不是这三项 caller input cause。命令/选项 grammar 尚未成功解析的 parser rejection 仍是 argument failure，不属于 handled `blocked`；recognized Question/configuration raw value 的领域类型、范围或路径校验则按后续 ADR 0094 留在 handled gate。ADR 0028 的“输入错误记为 failed”是跨工作流的早期广义默认；本 ADR 对 `knowledge.ask` pre-Answer CLI outcome 作更具体的后续窄化，三项 Question 输入错误改为 `blocked`，但仍不自动重试，也不改变其他 Context 的分类。

`failed` 表示 Gezhi 未能安全形成、验证或提交本次新 Answer，例如本次 staging/terminal materialization、manifest 形成或复验、target conflict、目录 rename 或其他本地提交不变量失败；它不能伪装成 caller-blocked。若普通 Answer validation/rendering failure 仍成功形成并提交 `status=failed` terminal Answer，则已经属于 ADR 0092 的 committed matrix，不属于本 ADR；这里只覆盖该故障阻止本次 terminal record 或目录 commit 的情形。ADR 0095 已将具体分支闭合为七项 primary code/context 并冻结内部优先边界，不授权 catch-all code 或根据异常文本猜分类。

`interrupted` 只表示 ADR 0098 的 command-owned cancellation latch 在原子 pre-ID barrier 先于本次新 `answer_id` cutover 线性化，并且 ADR 0099 的 `NoCommitSafeBoundaryV1` 已证明所有适用 operation、句柄与协调资源安全收尾；这些条件先建立 provisional interruption，最终没有 ADR 0095 的七项 failed candidate 时才由 ADR 0097 选择 `interrupted`。ID 一旦成功生成、验证并锁存，取消必须按既有 Answer 生命周期安全收尾并尝试形成、验证和提交完整 `status=interrupted` Answer：提交成功走 ADR 0092 的 committed matrix；terminalization、manifest 或目录 commit 失败且仍可安全报告时走本表 `failed`；teardown 始终无法证明安全时不进入本正常矩阵。单独 Ctrl+C observation、attempt `failure_class=interrupted`、Windows 外部强杀或进程消失本身都不足以构造 no-commit `interrupted` envelope；其他 terminal cause 已按既有规则锁存后，也不能为了返回 `interrupted` 而覆盖。ADR 0097 已固定同刻候选按 `failed > interrupted > blocked` 仲裁；ADR 0098 已冻结唯一 Ctrl+C bridge/latch、固定 checkpoints、work commitment、stop-new-work、final no-commit lock 与 identity cutover，ADR 0099 已冻结完整 drain、typed cleanup 与安全后置条件。ADR 0092 的 `knowledge.ask.user_interrupted.v1` 只判别 committed manifest；ADR 0096 已把 no-commit interruption 绑定为独立的 `knowledge.ask.user_interrupted_before_answer.v1`。

未提交 staging 中已经锁存、看似完整或甚至包含字面 terminal manifest 的 `status` 不是当前 CLI outcome 权威。Manifest/rename 失败后不得使用 would-be `status` 选择 `blocked/failed/interrupted`，也不得构造 `KnowledgeAskResultV1`；外部 no-commit terminal-cause classifier 独立选择本表的一行。只有 ADR 0090 的 non-replacing 同卷目录 rename 返回成功，result 才可非 `null` 并转入 ADR 0092 的 committed matrix。历史 orphan 的 validation、target conflict 或 recovery rename failure 只可成为后续 supplemental 事实，不能阻止本次新 ask 或充当其 primary；本次新 Answer 自己的对应形成/commit failure 才属于本表 `failed`。

每个合法非 `succeeded` envelope 仍按 ADR 0091 必须有且只有一个 index 0 primary，后面才可有 supplemental items。ADR 0094、ADR 0095 与 ADR 0096 已分别冻结 no-commit blocked、failed 与 interrupted primary，ADR 0097 已冻结跨 outcome 静态优先级，ADR 0098 已冻结 cancellation/identity linearization，ADR 0099 已冻结 `NoCommitSafeBoundaryV1`。任何路径都不能用空 diagnostics、通用 `no_commit_failed`、manifest error code、异常类型/text 或动态字符串临时填补；其他待决接口闭合前，完整 concrete `knowledge.ask` Schema 仍不可实现。

本 ADR 只覆盖“本次新 Answer 未 commit，但 Answer 编排与 teardown 已安全停止，Knowledge adapter 仍能形成 handled envelope”的路径。若 Job/子进程未证明静止、pipe 未到 EOF、collector/monitor 未 join、相关句柄/文件仍可能被触碰，或 writer ownership 不能安全释放，就不得承诺本表 outcome、primary、正常 envelope 或 exit；crash、强杀与 power loss 也不属于本矩阵。

上表的 process exit code 只适用于：`knowledge.ask --json` 已进入 handled path，no-commit terminal cause 与对应已冻结 primary 已通过完整 concrete validation，`result=null` 的合法 envelope 已成功写完，并沿正常 handled-return 结束。`130` 是受控中断的应用级返回值，不是 Windows 强制终止码或 Codex 子进程 Win32 DWORD；`2` 与参数解析或 [ADR 0116](./0116-return-2-with-one-fixed-stderr-line-for-raw-argv-resource-violation.md) raw argv resource failure 可能重号，但不把任一者归类为 `blocked`。ADR 0108 已把成功 seal/release 后的 `NO_OUTPUT_PRESENTATION_FAILURE`、stdout setup failure、completed invalid write count 与 I/O/broken-pipe failure 在证明无 outstanding/pending write 时独立映射为静默 exit `1`；它不使用本表，也不把该数值解释为业务 `failed`。ADR 0116 同样不使用本表或 ADR 0108，而由最小 bootstrap presenter 映射 fixed stderr/empty stdout/normal return `2`。其余 bootstrap/internal/argument、result/diagnostic/envelope 构造或 validation、Human mode、外部实际终止与 completion 不确定的 presentation failure 继续不由本表或 ADR 0108 映射，且不得打印 fallback envelope。

Knowledge command adapter 拥有 no-commit terminal-cause classification；ADR 0094、ADR 0095 与 ADR 0096 的静态 binding 分别将 blocked、failed 与 interrupted cause 绑定 versioned code，ADR 0097 的 cross-outcome arbiter 按 `failed > interrupted > blocked` 选择已经合法产生的候选，ADR 0098 的单一 cancellation state 以串行 commitment/checkpoint、原子 pre-ID barrier 与 final no-commit lock 划分 stop-new-work 和 Answer identity，ADR 0099 的 typed live-resource ledger 在 release 前冻结本地证据并证明 command-owned mutation 静止。共享 `DiagnosticSetV1` 只执行 role presence、唯一性、排序、容量与 omission，共享 JSON writer 只执行 outer/serialization/channel；只有 JSON writer 确认完整 envelope 写出成功后，normal-return exit adapter 才消费已经验证的 no-commit outcome。删除该分类 module 会迫使相同判断散落到输入、协调、staging、manifest、commit 与 presentation 调用方，因此该 seam 保持独立。

本决策本身不冻结 no-commit primary code/context union；blocked、failed 与 interrupted 已分别由后续 ADR 0094、ADR 0095、ADR 0096 冻结，跨 outcome 静态优先级已由 ADR 0097 冻结，cancellation/identity linearization 已由 ADR 0098 冻结，drain/cleanup 安全证明已由 ADR 0099 冻结，`knowledge.ask` JSON stdout cap/buffer 已由 ADR 0107 冻结，可控 JSON presentation failure exit 已由 ADR 0108 冻结，raw argv resource failure 已由 ADR 0116 独立闭合。Supplemental orphan/capture/maintenance variants、逐 code Human 中文文案、Human mode exit、CLI parser profile、其余 bootstrap/internal/argument 与 presentation failure exit、持久诊断资产、依赖、配置或模型调用仍不在本 ADR 范围内。

## 后续 presentation 收束

ADR 0100 后续冻结 `HandledCancellationWindowV1`，ADR 0107 又把 `knowledge.ask --json` 的 exact `outcome/result/diagnostics`、presentation disposition 与完整 payload 绑定给同一个 sealed candidate。Normal-return outcome/exit table 只有在 seal 成功、随后 accepted callback 已排空、Gezhi 自身 bridge 已移除并进入 `RELEASED`，且 `READY_BYTES` 完整 presentation 成功时才适用；`NO_OUTPUT_PRESENTATION_FAILURE` 与 write failure 不使用该表，只有满足 ADR 0108 的受控完成证明时才静默 exit `1`。Seal 后 Ctrl+C 不得重分类本 ADR 的 terminal cause；prior/default 实际终止即使数值偶合 `130`，也不是本 ADR 的应用级 normal-return `130`，且不得被改写为 ADR 0108 的 `1`。
