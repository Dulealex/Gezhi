# 用项目自有原生 Win32 DLL 实现 Ctrl+C bridge

`WindowsConsoleCancellationBridgeV1` 使用项目自有的 Windows x64 native DLL，并由 CPython 3.11 主编排线程通过标准库 `ctypes.WinDLL` 调用封闭导出接口。DLL 内的 C `HandlerRoutine` 以同一个稳定函数指针注册到 `SetConsoleCtrlHandler`；绝不把 Python、`ctypes.WINFUNCTYPE`、CFFI、pybind11 或其他运行时 callback 交给 Windows，也不允许 `signal.signal`、`KeyboardInterrupt` 或 Python default signal handler 写 ADR 0098 latch、选择 outcome 或参与 callback drain。该 DLL 只是 Gezhi CLI 的 console adapter，不是模型进程、Codex 可执行文件或第二套运行时；语义模型调用仍只经过项目冻结的 Codex CLI。

DLL module、routine thunk 与 control block 在第一次初始化后保持 process-safe lifetime，并在进程结束前不得 `FreeLibrary`、复用或释放给另一 invocation。Native handler 不调用 Python/C API、allocator、文件或 console I/O，不等待 Python、不抛异常、不终止进程、不执行 cleanup，也不取得可能由被中断线程持有的锁；它只使用固定 control block、Win32 atomic primitive 与 `QueryPerformanceCounter` 所需的有界操作。只有 `CTRL_C_EVENT` 可以参加 ADR 0100 admission：它在 `ACCEPTING` 通过同一 native atomic gate 赢得 admission 后，首次事件锁存 latch 与单调 observation，所有 accepted 重复事件保持首次 observation 不变，并为该事件固定返回 `TRUE`；其他 control type，以及在 `OUTSIDE`、`ARMED_PASS_THROUGH`、`SEALED_PASS_THROUGH` 或 `RELEASED` 才取得 admission 的 Ctrl+C，固定返回 `FALSE`。事件裁决不得在 handler 返回前重读 phase 后改判。

Python 只能从唯一主编排线程执行 register/activate、snapshot、conditional seal、accepted-callback drain、matching removal 与 phase proof。一次 admission 只有在同一 native gate 内已经保留 non-wrapping accepted generation、登记 accepted-in-flight，并为首次 Ctrl+C 完整发布 latch 与 QPC observation 后才算“callback 赢”；latch/observation、in-flight claim 与 publication-ready 必须先完成，generation 最后以 release 语义发布。Snapshot 只有取得同一 epoch 的 phase、generation、latch、observation、publication-ready 与 accepted-in-flight coherent acquire view 才可返回，否则只能 retry；conditional seal 必须同时核对 expected generation、publication-ready 且没有 admission writer 留在 publication critical section，不能只比较 generation。每个 accepted callback 在返回前 release-decrement 自己的 in-flight 登记；generation/token 溢出、torn/incoherent snapshot 或 counter 证明失败均不得 wrap、猜测或继续正常矩阵。

Python 先据 coherent snapshot 形成并完整验证候选 immutable `outcome/result/diagnostics` 与该 presentation mode 已批准的 closed disposition，为完整候选分配 nonzero、non-reused、non-wrapping `candidate_token`，并在唯一 command-owned pending slot 中把 expected generation、token、exact triple、disposition 及其完整 payload 一次性不可变绑定；不得先绑定 triple 后可变追加 presentation payload，token 不进入 CLI、diagnostic 或持久资产。[ADR 0107](./0107-seal-one-bounded-immutable-knowledge-ask-json-buffer.md) 已把 `knowledge.ask --json` payload 闭合为 `READY_BYTES` 的完整 envelope/exact canonical buffer/byte length，或 `NO_OUTPUT_PRESENTATION_FAILURE` 的完整 envelope/闭合 internal failure kind 与 absent buffer。Native conditional-seal 仍只需同时接收 expected generation 与 candidate token。若 callback 先赢 admission，seal 返回 retry，不改变 `ACCEPTING`、不记录 sealed token，Python 必须先废弃整个 pending candidate、payload 与 token，再重新消费 latch、仲裁并构造新候选；只有 coherent epoch 未变且 seal 在同一 atomic gate 先赢时，native 才在一个 release transition 中同时记录 `sealed_candidate_token=candidate_token` 并转为 `SEALED_PASS_THROUGH`。返回成功时 sealed token 必须与仍不可变存活的 pending slot 精确相等，该 exact triple 与 disposition/payload 自 native transition 起共同成为 authoritative final state；Python 随后的引用安装只是取得该既有事实，不建立第二个 seal。成功返回丢失、token mismatch、pending slot 改写/复用、payload identity 漂移或 sealed phase 无 matching token 都保持正常矩阵外。

Seal 成功后必须以 acquire proof 等待全部 seal 前 accepted-in-flight 归零，再以注册时同一 `HandlerRoutine` pointer 调用 `SetConsoleCtrlHandler(pointer, FALSE)`；matching removal 成功后才进入 `RELEASED`。注册、原子状态、generation、timestamp、candidate binding、drain、matching removal 或 ownership 任一项无法证明时保持 ADR 0100 的正常矩阵外。

Build-only 基线固定为现有 Visual Studio Build Tools 2022 `17.14.13`、x64 MSVC toolset directory `14.44.35207`（`cl 19.44.35215.0`、`link 14.44.35215.0`）与 Windows SDK `10.0.26100.0`。构建入口必须用 `vswhere.exe` 与已安装 toolset/SDK metadata 发现路径，不硬编码当前 `D:\` 安装位置，也不依赖调用者 PATH；DLL 使用 x64 release `/MT`，只链接项目代码、MSVC static runtime 与 Windows SDK，不需要 Python headers、CMake、Ninja 或新增 uv/npm 包。工具缺失或版本漂移只阻塞 native bridge build/test，实施阶段不得自动安装或升级；运行期只分发受项目验证的 DLL，并由 Python 标准库加载。

本 ADR 单独不声称 `SetConsoleCtrlHandler` registration 成功即可证明 OS 会投递 Ctrl+C，也不授权 `AllocConsole`、`AttachConsole`、`FreeConsole`、`GenerateConsoleCtrlEvent`、`SetConsoleMode` 或任何 NULL-handler call 来制造证明；后续 ADR 0102 是唯一获准的窄化例外，只允许 interactive candidate 在 activation 前对当前 standalone CLI 进程恰好调用一次 `SetConsoleCtrlHandler(NULL, FALSE)`，仍绝不允许 `NULL, TRUE`。后续 ADR 0103 已用只读 `CONIN$`/`GetConsoleMode` 冻结 attached console、`ENABLE_PROCESSED_INPUT`、stdin redirection 与 ConPTY/Terminal 候选门禁；后续 ADR 0104 已冻结 `capability_absent` 时不加载本 DLL、不注册 handler 且静默继续的 no-source profile，后续 ADR 0105 已冻结 `interactive_candidate` 在当前进程正被调试时也不加载本 DLL；[ADR 0106](./0106-run-command-owned-children-without-a-console.md) 已冻结 orchestrator-owned Codex attempt root 的 no-console/no-process-group 与 Job-owned stop，并继续禁止用 `GenerateConsoleCtrlEvent` 控制该 root。

后续 [ADR 0102](./0102-normalize-inherited-ctrl-c-ignore-before-activation.md) 已授权仅在 `interactive_candidate` 且 ADR 0105 已证明 `debugger_absent` 时，按 `register -> ARMED_PASS_THROUGH -> SetConsoleCtrlHandler(NULL, FALSE) -> ACCEPTING` 的顺序规范化当前 standalone CLI 进程；该 NULL call 既不用于 matching removal，也不恢复未知 inherited state。[ADR 0103](./0103-require-a-read-only-conin-processed-input-capability-gate.md) 已冻结 interactive candidate 的只读能力证明，[ADR 0104](./0104-continue-with-a-no-source-cancellation-profile-when-capability-is-absent.md) 已冻结 capability-absent no-source profile，[ADR 0105](./0105-use-the-no-source-profile-when-the-current-process-is-being-debugged.md) 已冻结 debugger-present no-source selection，[ADR 0106](./0106-run-command-owned-children-without-a-console.md) 已冻结 orchestrator-owned Codex attempt-root isolation。
