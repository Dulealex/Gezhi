## 职责与 seam

`CliResultEnvelopeV1` 是所有公开 Gezhi `--json` 命令共用的最小外部 interface。共享 CLI JSON writer module 隐藏 outer 组装、五字段 outer 与 JSON 可编码性验证、确定性 serialization 及 stdout 完整写出；concrete command adapter 必须先验证自己的 result/diagnostic Schema 与跨字段矩阵，writer 不拥有这些领域规则。Literature、Knowledge 和未来 Context 的 command adapter 不得自己输出 JSON，也不得依赖其他 Context 的实现。Human renderer 与 JSON writer 是同一 command outcome seam 上的两个 adapter；本合同不建立 Command Bus、动态插件机制或跨领域结果继承树。

## 封闭 outer

每个 concrete CLI JSON result 的 root 必须恰好包含以下五个 required key，root `additionalProperties=false`：

| field | required V1 rule |
|---|---|
| `schema_version` | 精确等于 `gezhi.cli_result.v1` |
| `command` | concrete command 固定的 ASCII dotted identifier；当前冻结 `doctor`、`status`、`knowledge.ask`、`literature.add`、`literature.resume` 与 `literature.review` bindings |
| `outcome` | 精确为 `succeeded`、`blocked`、`failed` 或 `interrupted` |
| `result` | command-owned JSON object 或 `null` |
| `diagnostics` | 0–16 项的非 `null` `CliDiagnosticItemV1` array；无 item 时为 `[]`，canonical array 不超过 16,384 bytes |

五项不得缺失、为别名或重复；不得增加第六个顶层 key。Outer 只规定 `result` 的 object/null union；`diagnostics` 的共享 item 与集合规则由 CLI Diagnostics v1 闭合。任何内部对象都不是自由键值袋；每个 concrete command 在可实现前必须另行冻结 result Schema、diagnostic code/context union、跨字段 presence matrix 与版本演进方式。

`schema_version` 版本化共享 CLI envelope generation，包括五字段 outer 与 CLI Diagnostics v1 的公共 item/array profile。增加遵守同一共享 interface 的 command 不需要升级它；改变 outer key、类型、outcome 值域/语义、serialization、channel contract 或公共 diagnostic profile 必须升级。Command-owned payload 若以后独立演进，必须使用其已冻结的嵌套 wire discriminator，或建立具有新 discriminator 的 outer/command concrete binding，不能静默重解释既有值。ADR 0090 的两字段 wrapper 使用后一规则，嵌套 `answer_output.schema_version` 独立版本化回答语义；versioned diagnostic `code` 独立判别各 diagnostic variant。

## outcome 语义

`outcome` 表示本次 CLI invocation 的终态，不表示 shell exit code，也不普遍复制被读取领域对象的历史状态。对本次 `knowledge.ask` 新创建并成功目录提交的 Answer，`outcome` 必须等于 terminal manifest `status`；提交点前不得发出声称该 Answer 已 committed 的 result。ADR 0092 已冻结此 committed 分支的 primary：`succeeded` 无 primary，`blocked/failed` 从 manifest error 静态一一映射，`interrupted` 使用 `knowledge.ask.user_interrupted.v1`。未提交 staging 中已经锁存或看似完整的 `status` 不是 outcome 权威。没有本次新 committed Answer 时，`result=null` 且禁止 `succeeded`；Question 领域输入或可恢复前置条件形成 provisional `blocked`，本地 Answer 形成、验证或目录提交失败形成 `failed`，同一 cancellation latch 在 atomic pre-ID barrier 先赢并完成安全收尾时形成 provisional interruption；ADR 0097 按 `failed > interrupted > blocked` 选择最终 no-commit outcome。一旦 `answer_id` 已成功生成、验证并锁存，安全取消必须尝试提交 interrupted Answer；提交失败属于 no-commit `failed` 或不安全矩阵外路径。ADR 0094、ADR 0095 与 ADR 0096 已分别冻结 `blocked` 的 11 项、`failed` 的 7 项与 `interrupted` 的 1 项 primary/context，ADR 0097 已冻结 no-commit 静态优先级，ADR 0098 已冻结 cancellation observation/work commitment、stop-new-work、final no-commit lock 与 identity cutover，ADR 0099 已冻结 typed live-resource ledger、完整 settle、cleanup/release 与安全后置条件；只有 `NoCommitSafeBoundaryV1` 成立才可锁存并发布 no-commit outcome。

这一 parity 仅适用于产生该 Answer 的 `knowledge.ask` invocation。未来 `knowledge.show` 成功读取历史 failed/blocked Answer 时，命令自身仍可 `outcome=succeeded`；启动时补交的旧 orphan Answer 也不是本次新 Answer，其历史 `status` 不支配当前 outcome。`search`、`doctor`、`status`、Literature 的双提交点和未来 Bot 也分别由自己的 concrete contract 决定。附属 orphan/warning diagnostic 不得单独覆盖已经确定的 invocation outcome。正常发布的 `answer_status=insufficient_evidence` 组合固定为 outer `outcome=succeeded`、manifest `status=succeeded`。

## 规范 bytes 与 channel

完整 envelope value 先通过 concrete Schema 与全部跨字段规则，再恰好执行等价 Python 3.11 serialization：

```python
json.dumps(value, ensure_ascii=False, allow_nan=False, sort_keys=True, separators=(",", ":")).encode("utf-8") + b"\n"
```

输出必须是 binary stdout 上恰好一个 JSON object 加一个末尾 LF：无 BOM、ANSI、raw CR、pretty print、第二个 value、`default` coercion、Unicode normalization 或平台换行转换。它不是 JSONL；`codex exec --json` 的 provider JSONL 只属于 Knowledge runtime adapter 与 attempt capture，绝不能直通为 Gezhi CLI outer。

Concrete `knowledge.ask` binding 在每个 coherent candidate generation 中，必须先把完整五字段 envelope 恰好整体序列化一次并形成 immutable buffer，再参加 conditional seal。完整 buffer 包括末尾 LF 的 cap 为 65,536 raw UTF-8 bytes inclusive；65,536 合法、65,537 拒绝。该数值由 ADR 0107 独立拥有，不继承 `manifest.json` cap。现有子合同给出 `A + D + 187 <= 49,338` bytes 的保守可证明上界，其中 embedded AnswerOutput canonical value `A <= 32,767`，diagnostics array `D <= 16,384`，因此合法当前 envelope 不会触发 cap。其他 command 必须另行证明并显式采用自己的 concrete cap；三个 Literature binding 已由 [Literature Commands v1](./literature-commands-v1.md) 独立采用含末尾 LF 的 32,768-byte inclusive cap。

`knowledge.ask` pending candidate 的 closed presentation disposition 只能是 `READY_BYTES` 或 `NO_OUTPUT_PRESENTATION_FAILURE`。前者把 exact triple、完整 envelope、唯一 buffer 与 byte length 一次性绑定给 candidate token；后者只处理 validated envelope 的 canonical serialization/cap invariant failure，buffer 必须 absent，且不得伪造第五种 outcome 或 diagnostic。Interactive callback 在 seal 前先赢时整项 candidate/token 作废并从新 coherent snapshot 重建；no-source profile 在 generation zero 的唯一逻辑 seal 中绑定同一 union。只有 seal 成功、profile-specific zero-in-flight/source release 完成并进入 `RELEASED` 后才允许第一个 stdout byte。

`knowledge.ask` 的 `READY_BYTES` writer 在 stdout 首次 I/O 前恰好一次 direct `msvcrt.setmode(1, os.O_BINARY)`，随后在同一 authoritative `bytes` 的 read-only、one-dimensional、C-contiguous view 上，从 offset zero 以 direct synchronous blocking `os.write(1, current_view)` 每次请求整个未写 suffix。Loop 只在 `offset < byte_length` 时进入；每次调用前在 catch 外证明 `remaining = byte_length - offset`、`current_view.obj is buffer`、`current_view.nbytes == requested == remaining` 与 `1 <= requested <= 65_536`。只有 `type(count) is int` 且 `1 <= count <= requested` 才推进实际 count；`count < requested` 是合法 short write，`bool`、其他非 `int`、`count <= 0` 与超请求 count 都是 invalid result。Writer 不得用 slicing 复制第二份 bytes。Production 只绑定 CPython 标准库 primitive；每个 `OSError` catch 只能包住一条 direct `setmode` 或 `os.write` 调用，其他异常原样逃逸。它只支持同步 CPython console、普通文件和 anonymous blocking byte pipe profile，不探测或修复继承的 nonblocking/overlapped/exotic endpoint，不设置 timeout，也不引入 background completion、第二 writer 或另一个需 flush 的用户态 buffer。只有 `offset == byte_length`、primitive 已接受完整 buffer 含末尾 LF 且没有 Gezhi-owned/background/overlapped pending write 时才可使用正常 outcome exit table；这不证明下游已读取或普通文件已持久化。成功 seal/release 且 completion 确定的 `NO_OUTPUT_PRESENTATION_FAILURE`、setup/write failure 按 ADR 0108 停止新 write 并恰好一次 `os._exit(1)`；完整 primitive contract 见 ADR 0109。

受支持且已经进入 handled `--json` path 的命令不向 stdout 写 Rich progress、spinner、prompt、日志、表格、traceback 或任何其他 bytes，也不把 handled 人用结果/进度复制到 stderr。Human mode 通过独立 adapter 呈现同一 command outcome。目录 commit 后、JSON acknowledgment 完成前仍可能崩溃；空或 partial stdout 不能证明 Answer 未提交。解释器/CLI bootstrap 前失败、ADR 0115 权威判定超限的 `RawArgvPreflightV1` resource failure、未知 command/option、recognized option 完全缺少参数、重复或互斥 grammar failure、外部强制终止或 ADR 0108 排除的 stdout failure 可能没有合法 envelope；不得用另一顶层形状冒充 V1。即使 preflight 看见 literal `--json`，它也不据此选择 JSON/Human mode；resource failure 不形成 handled result、outcome、diagnostic、cancellation 或 fallback envelope，而是由 ADR 0116 独立尝试 fixed stderr、保持 stdout empty 并返回 `2`。ADR 0108 闭合的 presentation failure 同样不生成 fallback envelope 或 diagnostic，只在其严格前置证明成立后静默 `os._exit(1)`。Top-level adapter 不得用 或 normal-return `130`。`DBG_CONTROL_C` 导致 alertable wait 返回/终止也只能按具体 operation 已批准的实际 return/completion 规则处理，不能依据推测因果制造 cancellation outcome 或 diagnostic。ADR 0094 已冻结 parser 只处理 grammar、recognized completion，ADR 0114 冻结全部资源计量排除 argv0，ADR 0115 冻结三个 ceiling、`len(str)` 单位、精确 aggregate、inclusive 判定与 raw-before-domain 顺序，ADR 0116 冻结 resource violation 的无 payload classification、dimension non-disclosure、fixed bytes/fd2 failure 与 exit `2`。[CLI Command v1](./cli-command-v1.md) 已冻结 controlled `CLI_BOOTSTRAP_FAILED` 与 `CLI_ARGUMENT_FAILED` 的非 JSON receipt；未被其 typed-verdict/grammar table 分类的 internal/entry fault 仍没有应用级 diagnostic 或 exit-code 映射。

`knowledge.ask` adapter 必须先按 ADR 0100 在同一原子 seal 中冻结并验证 `outcome`、`result`、`diagnostics` 与所选 presentation disposition；JSON `READY_BYTES` 还必须锁存完整 envelope、exact buffer 与 byte length，`NO_OUTPUT_PRESENTATION_FAILURE` 则锁存 absent buffer 与 internal failure kind。完成所选 cancellation profile 的 zero-in-flight 与 source-specific release proof 并进入 `RELEASED` 后，writer 或 Human renderer 才可开始 presentation。Seal 后 Ctrl+C 不得修改 immutable candidate 或制造新的 interrupted 结果；它可能经外部/prior/default 语义导致 stdout 为零字节、同一 buffer 的前缀或完整 envelope，均不得重试、修补或追加 fallback。只有 `READY_BYTES` 完整 presentation 成功并沿 handled return 返回时，既有 outcome-to-exit table 才适用；`NO_OUTPUT_PRESENTATION_FAILURE` 以及完成状态确定的 controlled setup/write failure 必须按 ADR 0108 无 cleanup/flush 地 `os._exit(1)`。外部/default termination、pending I/O、seal/release proof failure 即使数值偶合 `1` 或 `130`，也不属于该应用级选择。

Operations 与 Literature 不继承上述 Knowledge source、latch、profile 或 `RELEASED` lifecycle。它们分别按 [Operations v1](./operations-v1.md) 与 [Literature Commands v1](./literature-commands-v1.md) 建立 command-owned immutable outcome/buffer seal，并在 presentation 前 settle 且释放全部 command-owned child、write、handle 与 ownership；各自合同再拥有 cap、writer completion 与 presentation failure 规则。

## diagnostics 外置

`diagnostics` 只属于当前 invocation，不进入 Answer manifest、`assets`、Literature run、Knowledge Registry、SQLite、marker、sidecar 或 recovery 决策。它不能改变已提交领域对象、修复 staging/target 或成为后续命令的事实源。每项必须且只能含 versioned `code` 与 closed `context`；`succeeded` 没有 primary，其他 outcome 的 index 0 是唯一 primary；supplemental 同码聚合、按 code 排序，集合受 16-item/16,384-byte cap 约束，超限以保留的 `cli.diagnostics_omitted.v1` 收束。ADR 0092 已冻结 `knowledge.ask` committed primary subset，ADR 0093 已冻结 no-commit outcome 分类，ADR 0094、ADR 0095 与 ADR 0096 分别冻结 no-commit blocked、failed 与 interrupted primary subset，ADR 0097 已冻结跨 outcome 静态优先级，ADR 0098 已冻结 cancellation/identity cutover，ADR 0099 已冻结 `NoCommitSafeBoundaryV1`；[Operations v1](./operations-v1.md) 冻结 `doctor/status` 的完整 V1 diagnostic union 与 Human 映射；三个 Literature binding 已由 [Literature Commands v1](./literature-commands-v1.md) 冻结为无 supplemental 的完整 primary/Human 集合。`knowledge.ask` supplemental variants 与 Knowledge `search/show` 的 concrete union/Human 文案仍待冻结，完整共享规则见 [CLI Diagnostics v1](./cli-diagnostics-v1.md)。
## 首个 concrete binding

首个 binding 固定 `command="knowledge.ask"`。其 [Knowledge Ask Result v1](./knowledge-ask-result-v1.md) 已冻结为 `answer_id` 与 `answer_output` 两字段 process-level commit receipt：本次新 Answer 目录 commit 成功时 result 为该 object，`succeeded` 时嵌入完整 `AnswerOutputV1`，`blocked/failed/interrupted` 时 `answer_output=null`；本次没有新 committed Answer 时 `result=null`。[Knowledge Ask Diagnostics v1](./knowledge-ask-diagnostics-v1.md) 已冻结 committed Answer 的 15+1 primary union、两种 commit presence 下的 outcome matrix、no-commit blocked 的 11 项、failed 的 7 项与 interrupted 的 1 项 primary/context、blocked 内部仲裁、跨 outcome 静态优先级、cancellation latch/checkpoints、stop-new-work、atomic pre-ID barrier、`NoCommitSafeBoundaryV1`，以及完整合法 JSON 正常返回时 committed `0/2/1/130`、no-commit `2/1/130` 的 exit；ADR 0107 又冻结该 binding 的 prepared candidate、65,536-byte inclusive cap 与 same-buffer write，ADR 0108 冻结其 closed controlled presentation failure 的 `os._exit(1)`，ADR 0109 冻结 exact Windows stdout primitive，ADR 0110 冻结所有 CLI 共用、早于 command recognition 的 `RawArgvPreflightV1` seam/职责，ADR 0111 与 ADR 0119 冻结 PASS 后 typed checks、inert routing graph 与 selected-owning-adapter late load 的强入口边界，ADR 0113 冻结同一 snapshot 的 preflight/parser feed-through、关闭 Windows expansion 与 shell completion，ADR 0114 冻结资源计量排除 argv0，ADR 0115 冻结三个 inclusive raw ceilings、`len(str)` 单位与精确 aggregate，ADR 0116 冻结 resource violation 的 fixed fd2 line、empty fd1 与 normal exit `2`。[CLI Command v1](./cli-command-v1.md) 已冻结 controlled `CLI_BOOTSTRAP_FAILED` 与 `CLI_ARGUMENT_FAILED` 的非 JSON receipt。Supplemental variants、Human mode exit、未被 T02 typed-verdict/grammar table 分类的 internal/entry fault 与 ADR 0108 排除的 presentation failure 尚未冻结，不能用任意 dict、异常文本或临时字段填补。
