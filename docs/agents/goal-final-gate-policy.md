# Goal 最终审核策略

本策略补充 `docs/agents/goal-runbook.md`，适用于父 Spec `#1` 下的 `T01`–`T26`。如两份文档对人工检查点的描述不同，以本策略为准；其他授权边界、完成定义、依赖冻结和阻塞规则仍以运行手册为准。

## 审核模式

本轮实施采用“一个最终人工硬审核 + 一个自动软检查点”：

1. `T01`–`T08` 全部完成并合并后，协调器生成一次合同软检查点，但不暂停后续调度。
2. `T09`–`T26` 按原生依赖图继续自动实施、审查、合并和关闭。
3. `T26` 完成后停止推进，提交最终验收包，等待用户进行唯一一次人工硬审核。
4. 父 Spec `#1` 始终保持打开；只有用户最终验收后，才可在新的明确授权下关闭。

## T08 后的自动软检查点

软检查点必须作为父 Spec `#1` 的评论或可追溯文档保存，至少包含：

- 已冻结的 launcher、CLI、配置、诊断、Literature、Knowledge、Codex 子进程和 terminal Answer 合同；
- `T01`–`T08` 的 PR、commit 与测试证据；
- 尚存假设、已知风险及其下游影响；
- 冻结依赖与锁文件未漂移的证据；
- 继续执行 `T09`–`T26` 的 frontier 摘要。

该检查点用于早期暴露合同传播风险，不是人工批准门。生成后应立即重新计算 frontier，并继续所有可执行工单。

## 自主决策边界

在最终审核前，Codex 可以自主处理已经由 Spec、Issue、Context、ADR 或合同约束的实现细节，并应：

- 优先选择最小、可逆、可测试且不扩展范围的方案；
- 将新的可观察合同决定记录到对应 Issue、PR 或 ADR；
- 不借此策略新增、删除或升级依赖，不改变锁文件、模型供应商或冻结工具链；
- 不修改仓库权限、Secrets、可见性、保护规则，不发布 Release 或部署；
- 不关闭或改写父 Spec `#1`。

若信息不足只影响单个分支，应把对应工单标为 `needs-info` 并继续其他 frontier。若所有 frontier 都因同一问题耗尽，或者遇到凭据、权限、真实硬件、不可逆操作及无法由现有合同决定的产品选择，仍必须暂停并请求人工介入。最终审核模式不消除这些真实阻塞。

## 最终人工硬审核

最终审核包至少包含：

- `T01`–`T26` 的关闭状态、依赖图和验收追溯；
- 所有 PR、commit、独立审查与测试结果；
- Windows 确定性端到端测试和真实冻结环境 smoke 证据；
- launcher、八个命令、Human/JSON、恢复、Ctrl+C、引用闭环的演示或日志；
- 依赖与锁文件无漂移、`main` 与 `origin/main` 一致、无遗留实施 PR 或未知 worktree 的证明；
- 已知限制、`needs-info` 项和建议的后续范围。

用户最终审核通过前，只能声明“候选 V1 已完成”，不能声明父 Spec 已验收。若审核不通过，应重开受影响的子工单，或在父 Spec 下创建边界明确的修正工单，并根据合同影响重新计算下游复验范围；不得用一次笼统补丁掩盖传播影响。
